# Planning Modes, Farms and Cross-Project Surplus Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Three planning modes the group picks per project under "Plan for" in Settings, plus a Compare card that plans all three side by side — the user's "i think for the flow we need 3 algos 1) where it is the best raw mat / unit output cost 2) Cheapest way please also include machine material cost when thinking about this on this end 3) Best Multi Output for example 1 rubber tree farm with the crop manager could be centrifuged into rubber dust, wood pulp and carbon which takes care of half of the mats" — with the farms the group runs (Tree Growth Simulator, CropsNH Crop Manager, Forestry farms) as renewable sources the planner can build, and surplus that one project makes counted where another of the group's projects needs it.

**Architecture:** One new setting, `PlanSettings.objective` (`'least-raw' | 'cheapest' | 'multi-output'`), picks the solve's objective; add-on 12's build horizon stays its own setting and is read by `cheapest` and `multi-output` only. `least-raw` is add-on 12's "ignore build cost" (raw material per unit while running), `cheapest` is add-on 12's build-cost objective unchanged (raw over the horizon plus raw to build the machines the group lacks), and `multi-output` adds, inside add-on 12's build MIP, one binary per raw leaf the line buys, weighted by one horizon of the line's mean raw input per source (measured with the farm recipes off), so the plan needs as few distinct raw inputs as it can before cheapest overall decides. Farms enter the candidate graph as synthetic source recipes built per plan from the export's rows and the project's farm settings — Tree Growth Simulator per sapling row at the project's energy hatch tier, crop sticks under a Crop Manager per crop of the exported crop table, Forestry farms (and any farm the group already runs) as rates the group types in — with power, tool wear (priced, listed as upkeep) and their machine to build like any machine. Across projects, each project's latest cached plan publishes a small summary (surplus and external needs per good) that the other projects' plans read — never compute — so a line may take another project's surplus as a "from <project>" input up to its rate, and a multi-output line is credited for surplus another project needs; the plan cache key hashes what was read, draws never form a cycle, and a changed summary sends the SSE `plan` event to the projects that read it. The server plans the three modes for the Compare card on request, from the same plan cache, within a time limit.

**Tech Stack:** Node 24 (type stripping) · TypeScript 6.0.3 · highs 1.15.3 · React 19.3.0 · vitest 5.0.3 · @playwright/test 1.63.0 · the exporter mod's existing Java toolchain (no new dependency anywhere).

## Review Focus

1. **A project stored before this plan**, including one whose add-on 12 horizon is "Ignore build cost" (`buildHorizonHours: null`): it opens as "Least raw material" (null) or "Cheapest" (anything else), plans exactly as before, and a stale tab that still sends `{ buildHorizonHours: null }` switches the project to least raw rather than failing.
2. **A farm the group cannot build and does not own** (the Tree Growth Simulator is an IV craft; an MV project with no TGS in the scan or the manual list): it is never planned new, in any mode; one the group owns is used, and a Make N batch never adds one.
3. **Two projects that feed each other** (A makes surplus Wood Pulp that B takes "from A"; A plans for best multi-output and is credited for B's need): after each is planned twice nothing changes any more, and B's draw on A is refused while A draws on B (no cycle).
4. **The project that published a surplus is deleted, renamed, re-targeted or not planned since a restart**: the reader's "from <project>" input goes away or follows the new name and rate on its next plan, with the SSE `plan` event sent; the plan never fails because of another project.
5. **The Compare card on a slow or failing mode** (one mode hits the time limit, or a mode has no plan at all): the card shows the finished modes, says which one is still planning or why it failed, fills in when it finishes, and "Use this mode" works for any finished one.

## Architecture change requests

All of these become one architecture §11 entry numbered **45** (41 add-on 14, 42 Plan 6, 43 add-on 16, 44 add-on 15; 39 is add-on 12's), appended in Task 1 Step 4; its amendments to §6.3, §7, §8, §11.28 and §11.39 stay inside entry 45:

1. **Planning modes.** `PlanSettings.objective?: PlanObjective` with `PLAN_OBJECTIVES = ['least-raw', 'cheapest', 'multi-output']`, default `DEFAULT_OBJECTIVE = 'cheapest'`. `least-raw` = raw material per unit while running (add-on 12's "ignore build cost": no build model, plan 09's stages); `cheapest` = add-on 12's build-cost objective unchanged; `multi-output` = `cheapest` plus a fixed weight per distinct raw source (change request 3). The horizon (`buildHorizonHours`, §11.39) stays its own setting and is read by `cheapest` and `multi-output` only; a stored `null` horizon means "least raw" for a project without `objective` (normalizeSettings), a settings patch `{ buildHorizonHours: null }` without `objective` also sets `objective: 'least-raw'` (stale tabs), and a patch that sets `cheapest` or `multi-output` while the horizon is `null` also sets it to 24. `buildCostCounts(settings)` (§11.39) becomes `objectiveOf(settings) !== 'least-raw' && (Make N || horizon set)`; the client's horizon presets lose "Ignore build cost" (the mode carries it). Why `cheapest` is the default: spec §3.3 (changed 2026-10-18 at the user's request) already counts the machines the group lacks, add-on 12 builds exactly that with a 24 h horizon, and every project planned since add-on 12 merged plans that way — keeping it the default changes no stored project's plan.
2. **Farms as renewable sources.** `PlanSettings.farms?: FarmSettings` (`src/shared/types/farm.ts`; kinds `tgs` and `crop-manager` on by default; the Tree Growth Simulator's hatch tier, tools per mode and tool material; the Crop Manager's tier, seed stats, layers, liked biome tags, sky and fertilizer; `running`: farms the group already runs — Forestry multifarms and any other — as outputs per minute). The planner builds synthetic farm recipes per plan (`Recipe.meta.farm: FarmRecipeMeta`, source `derived`, ids from `recipeId`): Tree Growth Simulator recipes from the export's `gt.recipe.treefarm` rows (the loader records each output's mode as `meta.tgsModes`) on map `gt.recipe.treefarm`, crop recipes from the exported crop table (`Pack.crops`, change request 6) on the pseudo map `farm:crops` whose machines are the Crop Managers (28001–28012). A farm recipe runs at its own tier, never overclocked, on the farm machines the group owns or can build at the tier (Make N: owns), and its products are walked like add-on 12's gathered blocks, in every mode (`LeafDecision.farmMade`, beside add-on 12's `alsoMade`). Tool wear is a consumed input at the tool's price (`makeLeafOracle`'s `fixed` goods, never walked), listed as upkeep (`RawInput.upkeep`). `PlanStep.farm?: FarmStep`. `LinePricing.pack` is the pack with the line's farm recipes (`withFarms`), which `planLine` uses for everything after pricing; the layout handles a farm step from `PlanStep.farm` before it looks anything up. Running farms are capped free supplies (change request 4's columns) shown as "from <farm>".
3. **The multi-output weight.** In the build MIP each bought raw good (a purchase column whose cost is above 0, not an upkeep good) gets a binary `s_j` with `x_j − M_j·s_j ≤ 0` (M as add-on 12's derived-purchase binaries) and cost `SOURCE_WEIGHT_HORIZONS × s1f × F / (max(1, k1f) × σ)`, where `s1f` and `k1f` are the least raw material and its count of raw sources with the farm recipes off (`S1f`, also the step charge's measure on farm-fed lines): one horizon of the line's mean raw input per source, so the mode pays up to one average input's worth of raw material, machines included, to need one input fewer, and never more. `Solution.sources`, `Plan.rawSources`.
4. **Across projects.** Each project's latest plan (rate mode) publishes a `PublishedSummary` (surplus and external needs per good per second, its draws, its upstream projects) kept in the database's `meta` table (`Db.getMeta/setMeta/deleteMeta`, no schema change). A plan reads — never computes — the summaries of the other live projects on the same export: offers (another project's surplus of a good its candidate graph uses, unless that project draws on it, directly or through others) enter its LP as capped free supply columns (`SolveOptions.supplies`, shown as `RawInput.from`), and in `multi-output` the needs of other projects for goods it can make enter as capped credit columns (`SolveOptions.credits`, `Plan.credits`). `PlanSettings.useSurplus?: boolean` (default true). The plan cache key (§7) gains `|x:<hash of what was read>`; a published summary that changes sends the SSE `plan` event (§8) to the projects that read any of its goods, and a deleted project's summary is removed the same way.
5. **Compare.** `GET /api/projects/:id/compare` → `CompareResult` (`src/shared/types/api.ts`): per mode its status, summary (raw per hour, raw to build, new machines, distinct raw sources, steps, peak EU/t) and differences (raw inputs it avoids and adds against the other two), from the plan cache (one settings hash per mode), within `COMPARE_TIME_LIMIT_SECONDS`; modes still planning finish in the background and send SSE `event: compare` `data: {rev}`. Compare plans never publish summaries.
6. **Crop table export.** Exporter section `crops` writes `crops.jsonl.gz` from CropsNH's crop registry by reflection (optional; skipped without CropsNH); the loader fills `Pack.crops?: CropCard[]`. Without it crop farms are not offered and the plan says so once (`farm-data-missing`).
7. **Layout.** A farm step is laid out as a reserved area, not block by block: `Layout.reserved?: ReservedArea[]`, `Pin.kind` gains `'farm'`, one plain build step per farm (footprint, what to plant and put in its buses, which hatch); the 3D view, the Connections view and the ghost projector do not show farms, and the line's power and logistics hookups do not reach them (their build step says how to connect them).

**The model.**
- *Columns.* `mainLp` gains one column per supply after the sinks (`+1` in its good's row, upper bound `perSecond / scale` at unit demand, cost 0 in every stage) and one per credit (`−1` in its good's row, the same bound, cost 0 except below). The loop guard fixes supplies to 0 with the purchases (they are sources).
- *S1f.* When the graph has `farm` recipes, S1 again with them off (`x_j ≤ 0`): `s1f` and `k1f` (its distinct raw sources, counted as `Solution.sources` is); when that LP fails, `s1f = s1`, `k1f = k1`; without farm recipes both are S1's. `Solution.farmFree = { raw: s1f, sources: k1f }` (scaled like `rawCost`). On add-on 12's path its S1g is solved with the farm recipes off as well (σ never counts farm output as free); on plan 09's path (least raw) the step-charge MIP charges `stepCharge × max(s1, s1f)` per step (the cap stays `(1 + STEP_CHARGE_CAP) × s1`), so a farm-fed line whose least raw is only tool wear does not keep steps that save almost nothing.
- *Multi-output.* With `opts.multiOutput` and a counting build model, `buildMip` gets `sources = { columns: the purchase columns of goods with cost > 0 not in upkeep, weight: sourceWeight({ s1f, k1f, F, sigma: σ }) }`: a binary `s_j` per column with `x_j − M_j·s_j ≤ 0`, `M_j` as add-on 12's derived-purchase binaries (`obj(start) / c_j × (1 + 1e-6) + TINY`, `c_j` the column's objective coefficient), cost `weight`, `s_j = 1` in the start where `x1` buys; and `credits = [{ j, credit }]` whose columns cost `−credit × F / σ` (start 0). Without `multiOutput` neither is passed and credits stay at cost 0. Why the weight: a raw input the line no longer needs is worth what an average input of the farm-free line costs over the same horizon the machines are weighed against — the mode then pays up to one such input's worth of raw material, machines and step charges included, to need one input fewer, never more, and scales with the line's own size; measured without farms so that a line whose least raw material is only tool wear still values the inputs its farm replaces. The mean, not the median: a line with one large metal input and several small ones would otherwise value dropping a small one at almost nothing, which is the case this mode exists for.

**Data flow, caching, invalidation and live updates.**
1. `planForProject` works out the line's goods once per plan key (`planCacheKey(...)`, kept in an LRU map of 32 per app): the goods of `linePricing(pack, settings, ctx).graph` (the candidate walk never reads other projects, so its goods do not depend on them).
2. It reads the board (`crossRead`) — other projects' published summaries only; it never plans or changes another project — and, when publishing, notes the goods it read (`noteRead`).
3. The plan cache key becomes `planCacheKey(...)` plus `|x:<hash>` when the hash is not empty, so a project's plan is recomputed exactly when what it reads changed; a miss plans with `planLine(pack, settings, ctx, { offers: read.offers, needs: read.needs })`.
4. After planning it publishes `summaryOf(...)` (or removes its summary when there is none) in the database's `meta` table under `surplus:<id>` — summaries survive a restart, and a summary of another export is never read — and sends `event: plan` `data: {rev}` to each reader of a changed good (`readers(changed, id)`), whose tabs refetch as they do today; their plan route then reads the new summary, gets a new key and replans.
5. Deleting a project removes its summary (same fan-out); renaming one republishes its summary under the new name (the readers' hashes include names, so their "from <project>" rows follow); restoring one republishes on its next plan.
6. No cycles: a project never draws on one whose summary lists it upstream. A multi-output project reads the other projects' needs as their whole external demand (bought plus drawn), which does not change when a reader switches from buying a good to drawing it from this line, so a producer credited for a need and its reader that draws on it settle instead of trading the good back and forth.
7. Make N projects neither publish nor read (a batch has no steady surplus).

## Open questions

1. **Farms on for projects stored before this plan.** Farms are on by default (both kinds), so an existing project's plan may change where an owned Tree Growth Simulator or a new Crop Manager pays off under its mode. The alternative is a recorded "Planner update" that turns farms off for projects stored before this plan (plan 09's `settingsVersion` pattern). This plan keeps them on because the user asked for farms as sources; Task 1 is the one place to change if the user prefers the migration.
2. **The crop table needs a new export.** Crop farms on real data wait for Task 3's controller step (exporter 0.5.0 on a server copy, and the user's agreement to switch the active export); the Tree Growth Simulator works on today's export.
3. **Two readers of one producer's surplus.** Each reader may take up to the producer's whole surplus, so two readers can count the same goods. Options: leave it (today), warn on the producer when its readers' draws together exceed its surplus, or allocate by project age. Allocating makes a reader depend on other readers' plans, which this plan avoids to keep the reads acyclic.
4. **The source weight.** `SOURCE_WEIGHT_HORIZONS = 1` (one horizon of the farm-free line's mean raw input per source). A project setting could expose it later; this plan does not, so the three modes stay three.
