# Planning Modes, Farms and Cross-Project Surplus Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Three planning modes the group picks per project under "Plan for" in Settings, plus a Compare card that plans all three side by side — the user's "i think for the flow we need 3 algos 1) where it is the best raw mat / unit output cost 2) Cheapest way please also include machine material cost when thinking about this on this end 3) Best Multi Output for example 1 rubber tree farm with the crop manager could be centrifuged into rubber dust, wood pulp and carbon which takes care of half of the mats" — with the farms the group runs (Tree Growth Simulator, CropsNH Crop Manager, Forestry farms) as renewable sources the planner can build, and surplus that one project makes counted where another of the group's projects needs it.

**Architecture:** One new setting, `PlanSettings.objective` (`'least-raw' | 'cheapest' | 'multi-output'`), picks the solve's objective; add-on 12's build horizon stays its own setting and is read by `cheapest` and `multi-output` only. `least-raw` is add-on 12's "ignore build cost" (raw material per unit while running), `cheapest` is add-on 12's build-cost objective unchanged (raw over the horizon plus raw to build the machines the group lacks), and `multi-output` adds, inside add-on 12's build MIP, one binary per raw leaf the line buys, weighted by one horizon of the line's mean raw input per source (measured with the farm recipes off), so the plan needs as few distinct raw inputs as it can before cheapest overall decides. Farms enter the candidate graph as synthetic source recipes built per plan from the export's rows and the project's farm settings — Tree Growth Simulator per sapling row at the project's energy hatch tier, crop sticks under a Crop Manager per crop of the exported crop table, Forestry farms (and any farm the group already runs) as rates the group types in — with power, tool wear (priced, listed as upkeep) and their machine to build like any machine. Across projects, each project's latest cached plan publishes a small summary (surplus and external needs per good) that the other projects' plans read — never compute — so a line may take another project's surplus as a "from <project>" input up to its rate, and a multi-output line is credited for the byproducts it makes that another project needs; the plan cache key and the layout key hash what was read, one read, plan and publish runs at a time and draws are checked against the board as it is, so they never form a cycle, and a changed summary sends the SSE `plan` event to the projects that read it, damped so that plans that keep changing each other stop within one round. The server plans the three modes for the Compare card on request, one after another, from the same plan cache and one line pricing, one compare per project at a time, within a time limit.

## Review Focus

1. **A project stored before this plan**, including one whose add-on 12 horizon is "Ignore build cost" (`buildHorizonHours: null`): a rate project opens as "Least raw material" (null) or "Cheapest" (anything else) and a Make N project as "Cheapest" (add-on 12 always counted a batch's build cost); each plans as before except where this plan's new defaults change it — farms (both kinds on) and "Use other projects' surplus" (on), open question 1; a stale tab that still sends `{ buildHorizonHours: null }` switches the project to least raw, one that sends a horizon to a least-raw project switches it to cheapest, and neither fails; a project created with `{ buildHorizonHours: null }` is least raw.
2. **A farm the group cannot build and does not own** (the Tree Growth Simulator is an IV craft; an MV project with no TGS in the scan or the manual list): it is never planned new, in any mode; one the group owns is used, and a Make N batch never adds one.
3. **Two projects that feed each other** (A makes surplus Wood Pulp that B takes "from A"; A plans for best multi-output and is credited for B's need): after each is planned twice nothing changes any more, and B's draw on A is refused while A draws on B (no cycle) — also when both are planned at once, and when the circle would close through a third project whose summary is older than the draw that closes it.
4. **The project that published a surplus is deleted, renamed, re-targeted or not planned since a restart**: the reader's "from <project>" input goes away or follows the new name and rate on its next plan, with the SSE `plan` event sent; the plan never fails because of another project.
5. **The Compare card on a slow or failing mode** (one mode hits the time limit, or a mode has no plan at all): the card shows the finished modes, says which one is still planning or why it failed, fills in when it finishes, and "Use this mode" works for any finished one — and publishes that mode's summary, though the card had already planned it; settings changed while a compare runs never stack compares: the newest settings win.
6. **Plans that keep changing each other** (A's credit changes A's surplus, which changes B's needs, which changes A's credit) while both have tabs open: the fan-out stops within one round, each replanned at most once, and the plan whose fan-out stopped says so (`surplus-loop`).

## Architecture change requests

All of these become one architecture §11 entry numbered **45** (41 add-on 14, 42 Plan 6, 43 add-on 16, 44 add-on 15; 39 is add-on 12's), appended in Task 1 Step 4; its amendments to §6.3, §7, §8, §11.28 and §11.39 stay inside entry 45:

1. **Planning modes.** `PlanSettings.objective?: PlanObjective` with `PLAN_OBJECTIVES = ['least-raw', 'cheapest', 'multi-output']`, default `DEFAULT_OBJECTIVE = 'cheapest'`. `least-raw` = raw material per unit while running (add-on 12's "ignore build cost": no build model, plan 09's stages); `cheapest` = add-on 12's build-cost objective unchanged; `multi-output` = `cheapest` plus a fixed weight per distinct raw source (change request 3). The horizon (`buildHorizonHours`, §11.39) stays its own setting and is read by `cheapest` and `multi-output` only. In rate mode a `null` horizon means "least raw" whatever `objective` says (`objectiveOf`: it is add-on 12's "Ignore build cost", and settings built as `{ ...defaultSettings(), buildHorizonHours: null }` — add-on 12's test helpers — mean exactly that); `normalizeSettings` stores `objective: 'least-raw'` for such a project and `'cheapest'` for a Make N project with a stored `null` horizon (add-on 12 always counted a batch's build cost). The rules on a settings patch (`withObjectiveRules`, also applied by the create route, whose `normalizeSettings({ ...defaultSettings(), ...settings })` would otherwise keep the defaults' `cheapest` beside a `null` horizon): `{ buildHorizonHours: null }` without `objective` also sets `objective: 'least-raw'` (stale tabs); a non-null horizon without `objective` on a least-raw project also sets `objective: 'cheapest'` (a stale tab that picks a horizon); and a result whose objective is `cheapest` or `multi-output` with a `null` horizon gets 24. `buildCostCounts(settings)` (§11.39) becomes `objectiveOf(settings) !== 'least-raw' && (Make N || horizon set)`, `Plan.cost.horizonHours` (§11.39) becomes `horizonHoursOf(settings)` (null in least raw, so the cost line says build cost is not counted), and every other server read of `buildHorizonHours` that decides how a plan counts build cost goes through `objectiveOf`/`horizonHoursOf`; the client's horizon presets lose "Ignore build cost" (the mode carries it). Why `cheapest` is the default: spec §3.3 (changed 2026-10-18 at the user's request) already counts the machines the group lacks, add-on 12 builds exactly that with a 24 h horizon, and every project planned since add-on 12 merged plans that way — keeping it the default keeps every stored project's mode (the new farm and surplus defaults are open question 1).
2. **Farms as renewable sources.** `PlanSettings.farms?: FarmSettings` (`src/shared/types/farm.ts`; kinds `tgs` and `crop-manager` on by default; the Tree Growth Simulator's hatch tier, tools per mode and tool material; the Crop Manager's tier, seed stats, layers, liked biome tags, sky and fertilizer; `running`: farms the group already runs — Forestry multifarms and any other — as outputs per minute). The planner builds synthetic farm recipes per plan (`Recipe.meta.farm: FarmRecipeMeta`, source `derived`, ids from `recipeId`): Tree Growth Simulator recipes from the export's `gt.recipe.treefarm` rows (the loader records each output's mode as `meta.tgsModes`) on map `gt.recipe.treefarm`, crop recipes from the exported crop table (`Pack.crops`, change request 6) on the pseudo map `farm:crops` whose machines are the Crop Managers (28001–28012). A farm recipe runs at its own tier, never overclocked, on the farm machines the group owns or can build at the tier (Make N: owns), and its products are walked like add-on 12's gathered blocks, in every mode (`LeafDecision.farmMade`, beside add-on 12's `alsoMade`). Tool wear is a consumed input at the tool's price (`makeLeafOracle`'s `fixed` goods, never walked), listed as upkeep (`RawInput.upkeep`). `PlanStep.farm?: FarmStep`. `LinePricing.pack` is the pack with the line's farm recipes (`withFarms`), which `planLine` uses for everything after pricing; the layout handles a farm step from `PlanStep.farm` before it looks anything up. Running farms are capped free supplies (change request 4's columns) shown as "from <farm>".
3. **The multi-output weight.** In the build MIP each bought raw good (a purchase column whose cost is above 0, not an upkeep good) gets a binary `s_j` with `x_j − M_j·s_j ≤ 0` and cost `SOURCE_WEIGHT_HORIZONS × s1f × F / (max(1, k1f) × σ)`, where `s1f` and `k1f` are the least raw material and its count of raw sources with the farm recipes off (`S1f`, also σ's measure on farm-fed lines): one horizon of the line's mean raw input per source, so the mode pays up to one average input's worth of raw material, machines included, to need one input fewer, and never more. `M_j = (obj(start) + Σ_c upper_c·credit_c·F/σ) / c_j × (1 + 1e-6) + TINY` (`upper_c` a credit column's bound): add-on 12's derived-purchase M (what a plan no dearer than the start can buy) plus the most the credit columns (change request 4) can earn, since a plan that earns credits may buy more than `obj(start)/c_j`; add-on 12's derived-purchase binaries take the same M when credits are present. The multi-output MIP starts from cheapest's decision (the build MIP solved first without source binaries or credits) when that is better in its objective than add-on 12's start, the purchases whose `s_j` it sets to 0 stay out of add-on 12's later stages (`BuildDecision.dropped`: those stages minimize raw material again and would buy a dropped source back), and a plan from add-on 12's fallback carries `sources-approx` as well. Tool wear (upkeep) is no raw source — research §5.1 counts tools, fertilizer and compost as raw; this plan counts a crop farm's fertilizer but not tools, which are stocked parts worn by a fraction per operation, since counting them would charge every tree farm two sources for its saw and knife, the inputs this mode exists to drop (README). `Solution.sources`, `Plan.rawSources`.
4. **Across projects.** Each project's latest plan (rate mode) publishes a `PublishedSummary` (surplus and external needs per good per second, and its draws) kept in the database's `meta` table (`Db.getMeta/setMeta/deleteMeta`, no schema change). A plan reads — never computes — the summaries of the other live projects on the same export: offers (another project's surplus of a good its candidate graph uses, not one of its own targets, unless that project draws on it, directly or through others, on the board as it is when read: the draws are walked at read time, never taken from a list the producer stored when it last published) enter its LP as capped free supply columns (`SolveOptions.supplies`, shown as `RawInput.from`), and in `multi-output` the needs of other projects for goods it can make enter as capped credit columns (`SolveOptions.credits`, `Plan.credits`), each limited to the byproduct the line's own recipes make of the good less what the line uses of it (never a purchase, a supply, or a recipe whose main output it is). `PlanSettings.useSurplus?: boolean` (default true). The plan cache key (§7) gains `|x:<hash of what was read>`, and the plan carries it (`Plan.crossHash`), so Plan 5's layout key (§11.8) gains it too. One read, plan and publish runs at a time per app (`SurplusBoard.exclusive`), and every plan request that publishes publishes, cache hit or miss; a summary whose surplus or needs change sends the SSE `plan` event (§8) to the projects that read those goods, a changed name to the readers of all its goods, and changed draws to every project that read offers (their circle checks walk the draws); a deleted project's summary is removed the same way. Within `FANOUT_ROUND_SECONDS` a fan-out never goes back to a project whose change led to it, and the plan whose fan-out stopped carries `surplus-loop`.
5. **Compare.** `GET /api/projects/:id/compare` → `CompareResult` (`src/shared/types/api.ts`): per mode its status, summary (raw per hour, raw to build, new machines, distinct raw sources, steps, peak EU/t), differences (raw inputs it avoids and adds against the other two) and the goods it is credited for, from the plan cache (one settings hash per mode) and one line pricing (`linePricing`'s memo key leaves out `objective`, `useSurplus` and the horizon and keeps `buildCostCounts(settings)`, which is all of them its pricing reads), the modes planned one after another, the current one first, within `COMPARE_TIME_LIMIT_SECONDS`; one compare per project at a time (the newest settings win, as `replanInBackground`), at most `COMPARE_MAX_RUNNING` projects at once per app; modes still planning finish in the background and send SSE `event: compare` `data: {rev}`. Compare plans never publish summaries.
6. **Crop table export.** Exporter section `crops` writes `crops.jsonl.gz` from CropsNH's crop registry by reflection (optional; skipped without CropsNH); the loader fills `Pack.crops?: CropCard[]`. Without it crop farms are not offered, and the Farms section of Settings says so (the export's manifest has no `crops` count); no plan carries a note for it (every plan would, until the active export is switched).
7. **Layout.** A farm step is laid out as a reserved area, not block by block: `Layout.reserved?: ReservedArea[]`, `Pin.kind` gains `'farm'`, one plain build step per farm (footprint, what to plant and put in its buses, which hatch); the 3D view, the Connections view and the ghost projector do not show farms, and the line's power and logistics hookups do not reach them (their build step says how to connect them). What a farm step sends to the line counts as a raw input of the line's input chest (direct, routed), as EnderIO's entering flows already count it.

**The model.**
- *Columns.* `mainLp` gains one column per supply after the sinks (`+1` in its good's row, upper bound `perSecond / scale` at unit demand, cost 0 in every stage) and, with `opts.multiOutput` only, one per credit (`−1` in its good's row, the same bound, cost 0 except in the build MIP; without `multiOutput` no credit column exists and `credited` is empty). It may still run a byproduct's recipe beyond its own need when the credit pays for that recipe's inputs and machines (the split case of Step 1; the Compare card names the credited goods, Task 7; open question 5). The loop guard fixes supplies to 0 with the purchases (they are sources).
- *S1f.* When build cost counts and the graph has `farm` recipes, S1 again with them off (`x_j ≤ 0`): `s1f` and `k1f` (its distinct raw sources, counted as `Solution.sources` is); when that LP fails, `s1f = s1`, `k1f = k1`; otherwise both are S1's. `Solution.farmFree = { raw: s1f, sources: k1f }` (scaled like `rawCost`). On add-on 12's path its S1g is solved with the farm recipes off as well (σ never counts farm output as free, so add-on 12's step charge, `stepCharge × σ` raw per step, keeps its farm-free size). Plan 09's path (least raw) is unchanged: its charge MIP, whose objective is in units of S1, keeps plan 09's `stepCharge` per step. A charge against S1f there would weigh each step `stepCharge × s1f / s1` — 1,000 to 10,000 times plan 09's measured 0.01–0.02 on a farm-fed line whose least raw material is only tool wear, where plan 09 measured root nodes of 5–14 s at weights of 0.05–1 and the MIP has no time limit (`STEP_MIP_MAX_NODES = 1` only) — while its +25 % raw cap would still let it drop almost nothing. So a farm-fed least-raw line may keep a step that saves a little tool wear: least raw counts raw material only (README); Task 10 times such a line.
- *Multi-output.* With `opts.multiOutput` and a counting build model, `buildMip` gets `sources = { columns: the purchase columns of goods with cost > 0 not in upkeep, weight: sourceWeight({ s1f, k1f, F, sigma: σ }) }`: a binary `s_j` per column with `x_j − M_j·s_j ≤ 0`, cost `weight`, `s_j = 1` in the start where it buys; and `credits = [{ j, credit, upper }]` whose columns cost `−credit × F / σ` (start 0, `upper` the column's bound). `M_j = (obj(start) + Σ_c upper_c × credit_c × F / σ) / c_j × (1 + 1e-6) + TINY`, `c_j` the column's objective coefficient: add-on 12's derived-purchase M, `obj(start) / c_j × (1 + 1e-6) + TINY`, is what a plan no dearer than the start can buy only while every objective term is ≥ 0, and a plan that earns credits may buy more (Step 1's credit case needs 0.5 a/s where `obj(start) / c_a` allows about 0.4); add-on 12's derived-purchase binaries take the same M when credits are present. *Start.* The binaries' relaxation charges a source only `weight × x_j / M_j` (`weight × c_j·x_j / obj(start)` without credits), so branch-and-bound has to find the savings, within the node limit add-on 12 measured without them: `solveLine` first solves the build MIP as `cheapest` does (no source binaries, the credit columns fixed to 0; add-on 12's limits) and passes its solution as `BuildMipInput.start` — its whole machines, `s_j = 1` where it buys, credits 0: feasible — which the multi-output MIP starts from when its multi-output objective is below that of `roundUp(x1)`'s start; the multi-output plan is then never worse in its objective than cheapest's decision. *The later stages.* Add-on 12's stage 5 minimizes raw material again over the decision (its `off` = the step recipes outside its support), and nothing there stops it from buying again a source the MIP dropped where that is less raw than making it; so `decode` records the purchase columns whose `s_j` is 0 (`BuildDecision.dropped`) and stage 5 adds them to its `off` set, as plan 09's charge stage keeps out the derived purchases it left out (the MIP's own solution shows the rest stays feasible). *Fallback.* On add-on 12's fallback (the time guard, or no whole solution), whose relaxation rounded up ignores the binaries' savings, the plan also carries `{ code: 'sources-approx', text: 'Finding the fewest different raw materials took too long; this plan may need more of them than it could' }`; `Solution.sources` is always counted from the final plan. `Solution.buildStats` covers both MIPs (their seconds and nodes added up, the multi-output MIP's status and stop). Without `multiOutput` neither is passed. Why the weight: a raw input the line no longer needs is worth what an average input of the farm-free line costs over the same horizon the machines are weighed against — the mode then pays up to one such input's worth of raw material, machines and step charges included, to need one input fewer, never more, and scales with the line's own size; measured without farms so that a line whose least raw material is only tool wear still values the inputs its farm replaces. The mean, not the median: a line with one large metal input and several small ones would otherwise value dropping a small one at almost nothing, which is the case this mode exists for.

**Data flow, caching, invalidation and live updates.**
1. `planForProject` works out the line's goods once per plan key (`planCacheKey(...)`, kept in an LRU map of 32 per app): the goods of `linePricing(pack, settings, ctx).graph` (the candidate walk never reads other projects, so its goods do not depend on them).
2. With `publish` (the default), steps 2–4 run inside `board.exclusive`: one read, plan and publish at a time per app. Without it two plans could both read the board before either publishes and draw on each other — `planLine` awaits, and `replanInBackground` and the tabs' GETs of two projects interleave. Nothing inside calls `planForProject` again (the layout service's own call comes after the plan route's has returned), so the lock cannot deadlock. It reads the board (`crossRead`) — other projects' published summaries only; it never plans or changes another project — and notes what it read offers and needs of (`noteRead`). A compare plan (`publish: false`) reads without the lock and publishes nothing.
3. The plan cache key becomes `planCacheKey(...)` plus `|x:<hash>` when the hash is not empty, so a project's plan is recomputed exactly when what it reads changed; a miss plans with `planLine(pack, settings, ctx, { offers: read.offers, needs: read.needs })` and sets `Plan.crossHash = read.hash` (absent when `''`), which `layoutKey` adds, so the layout follows the plan.
4. Every call with `publish`, cache hit or miss — a compare may have planned the project's current mode, and "Use this mode" then hits that entry — publishes `summaryOf(...)` (or removes its summary when there is none) in the database's `meta` table under `surplus:<id>` — summaries survive a restart, and a summary of another export is never read — and sends `event: plan` `data: {rev}` to each project `fanOut(id, change)` gives, whose tabs refetch as they do today; their plan route then reads the new summary, gets a new key and replans. `publish` compares with the stored summary, so a hit that changes nothing sends nothing.
5. Deleting a project removes its summary (`remove`: every good and `draws: true`, fanned out the same way); renaming one republishes its summary under the new name, which reaches the readers of all its goods (their hashes include names, so their "from <project>" rows follow); restoring one republishes on its next plan.
6. No cycles: a reader never takes an offer from a project whose draws reach it on the board as it is when read (`crossRead`'s walk). A stored "upstream" list would date from the producer's last publish: C draws from B, so C's list is [B]; B then starts drawing from A, and B's publish changes no good C reads, so C's list stays [B] and A could take C's offer and close A → C → B → A. With one read, plan and publish at a time (step 2), every draw is published against the board it was read from, so the board's draws never close a circle (a draw that would close one is refused at its read, so a change of draws never undoes a draw a plan already has); a change of a project's draws reaches every project that read offers (`BoardChange.draws`), since its walk may pass through it — removed draws may allow an offer that was refused. A multi-output project reads the other projects' needs as their whole external demand (bought plus drawn), which does not change when a reader switches from buying a good to drawing it from this line, so a producer credited for a need and its reader that draws on it settle instead of trading the good back and forth.
7. Damping: `fanOut` gives each project it reaches the round it was reached in — the projects whose changes led there, plus `from` — kept `FANOUT_ROUND_SECONDS` (the board's clock), and leaves every project of `from`'s own round out of `from`'s fan-out. So plans that keep changing each other — A's credit changes A's surplus, which changes B's needs, which changes A's credit — stop within one round, each project replanned at most once by it, instead of replanning both projects, each a full plan on the shared thread, for as long as their tabs are open. A plan whose fan-out `skipped` someone is served with `{ code: 'surplus-loop', text: 'This plan and <names> keep changing what each other can use; <names> are not planned again for it now, only the next time they change' }` (added by `planForProject` to the plan it serves after that publish, not cached). A project left out plans with the newer summary on its next plan, whatever starts it.
8. Make N projects neither publish nor read (a batch has no steady surplus).

## Open questions

1. **Farms and other projects' surplus on for projects stored before this plan.** Farms are on by default (both kinds) and so is "Use other projects' surplus", so an existing project's plan may change where an owned Tree Growth Simulator or a new Crop Manager pays off under its mode, or where another of the group's projects has surplus of a good its line uses — it then takes it "from <project>" instead of buying or making it. (Its mode does not change: a rate project with "Ignore build cost" is least raw, every other one cheapest.) The alternative is a recorded "Planner update" that turns farms, the surplus switch or both off for projects stored before this plan (plan 09's `settingsVersion` pattern). This plan keeps both on because the user asked for farms as sources and for surplus to count across projects; Task 1 is the one place to change if the user prefers the migration.
2. **The crop table needs a new export.** Crop farms on real data wait for Task 3's controller step (exporter 0.5.0 on a server copy, and the user's agreement to switch the active export); the Tree Growth Simulator works on today's export.
3. **Two readers of one producer's surplus.** Each reader may take up to the producer's whole surplus, so two readers can count the same goods. Options: leave it (today), warn on the producer when its readers' draws together exceed its surplus, or allocate by project age. Allocating makes a reader depend on other readers' plans, which this plan avoids to keep the reads acyclic.
4. **The source weight.** `SOURCE_WEIGHT_HORIZONS = 1` (one horizon of the farm-free line's mean raw input per source). A project setting could expose it later; this plan does not, so the three modes stay three.
5. **Credits that grow a line.** A multi-output line is credited only for byproducts its own recipes make (never for a purchase passed through or a recipe run for the good itself), but it may still run a byproduct's recipe beyond its own need when another project's need pays for that recipe's inputs and machines — its raw per hour then goes up, and the Compare card names the goods it makes for other projects. Options: keep it (the group's total raw goes down: the other project takes the good "from" this one), or credit only the byproduct of the runs the line needs anyway (a second solve per multi-output plan, without the credits, to fix those runs first).
