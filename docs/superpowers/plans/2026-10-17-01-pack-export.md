# Pack Export & Data Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Export every recipe, item, fluid, machine, material and worldgen source of the group's own GTNH 2.9 pack from a throwaway copy of their server, and load it into an in-memory `Pack` (architecture §6.2) with indices, search and a `pack:info` CLI.

**Architecture:** A small Forge 1.7.10 mod (`exporter-mod/`, GTNH ExampleMod template) stays inert unless `-Dgtnhplanner.exportDir` is set; then, 100 ticks after the server has started, it runs a list of export sections that write gzip'd JSON Lines plus `manifest.json`, writes `EXPORT_OK`/`EXPORT_FAILED` and shuts the server down. A Node orchestrator (`npm run export`) APFS-clones the configured server folder into `.local/export-server/` (no world, backups, logs or player files), rewrites `server.properties` for a private FLAT world on 127.0.0.1:25566, installs the built jar, runs Java with the live start script's arguments under `nice` and a 15-minute watchdog, validates the result and activates it in `data/config.json`. The TypeScript pack loader streams the files into the architecture's `Pack` (item keys, wildcard expansion, chances 0..1, content-hash recipe ids, map aliases, derived furnace recipes, producer/consumer indices, materials, worldgen with a hand-maintained tier table) and `searchPack` ranks English names, registry names and ore names.

**Tech Stack:** TypeScript 6.0.3 on Node 24 (type stripping, `node:zlib`, `node:readline`, `node:child_process`), vitest 5.0.3; Java 8 bytecode (Jabel) built with GTNHGradle 2.0.33 / Gradle 9.7.1 against `GT5-Unofficial:5.09.54.183:dev`, Gson's streaming `JsonWriter` (ships with Minecraft 1.7.10).

**Spec:** `docs/superpowers/specs/2026-10-17-gtnh-planner-design.md` (§3.1, §3.3b data part, §3.12, §5, §6). Contracts: `docs/superpowers/plans/2026-10-17-00-architecture.md` (§2–§6.2, §9, §10) — authoritative. Facts: `docs/research/export-mod.md` (primary), `docs/research/materials-availability.md`, `docs/research/prior-art.md` §1.4 and §3.1–§3.2, `docs/research/gt-mechanics.md` §2.4 and §5, `docs/research/world-format.md` §6.3, `docs/research/web-stack.md` §1–§2. Local paths: `docs/local/environment.md` (never copied into this plan).

## Global Constraints

- Node `>=24.10.0 <25`; `"type": "module"`. TypeScript erasable syntax only (no `enum`, `namespace`, parameter properties, decorators, `<T>x`); relative imports name the real `.ts` file; type-only imports use `import type`. `src/shared/**` imports nothing from `node:*`.
- npm dependencies of this plan: exactly `typescript@6.0.3`, `@types/node@24.19.1`, `vitest@5.0.3` (dev). Install with `npm install --save-exact --before="$(date -v-14d +%F)" <pkg>@<ver>` and commit `package-lock.json`. No other npm package.
- tsconfig files are exactly web-stack.md §2.3, except that `tsconfig.json` references only the server project until Plan 2 adds the others (change request 1); vitest runs the `server` project with `experimental.viteModuleRunner: false` (Plan 2 adds the `client` project).
- Never start, stop or write to the live server or its folder. Exports run only on the APFS clone `.local/export-server/` (`server-port=25566`, `server-ip=127.0.0.1`, `level-name=export-world`, `level-type=FLAT`, `online-mode=false`, `white-list=true` with an empty whitelist, `max-tick-time=0`). The source folder is opened read-only (only `cp -c` reads it).
- Nothing game-derived or private is committed (spec §3.12): exports live in `data/export/<exportId>/`, the clone in `.local/`, run notes in `docs/local/`. No player names, UUIDs, coordinates, server address or absolute home paths in committed files.
- Tests use synthetic fixtures from `tests/helpers/` (`makeExport(dir, spec)`); anything reading real game files is skipped unless `process.env.GTNH_LOCAL === '1'`.
- Exporter mod: GTNH ExampleMod1.7.10 @ `6453dec5f5f534e604887d3505ddf7125889c6f9`, GTNHGradle (`com.gtnewhorizons.gtnhsettingsconvention`) `2.0.33`, Gradle `9.7.1`, daemon `toolchainVersion=25`, `enableModernJavaSyntax = jabel` (class version 52), `compileOnly("com.github.GTNewHorizons:GT5-Unofficial:5.09.54.183:dev")`, mod id `gtnhplannerexport`, package `io.github.drukoz.gtnhplanner.export`. Build from the repo root: `(export GRADLE_USER_HOME="$PWD/.local/gradle-home"; cd exporter-mod && VERSION=<v> ./gradlew assemble)`; install `build/libs/gtnhplannerexport-<v>.jar` (reobf/SRG), never the `-dev` jar.
- Export format id `gtnh-planner-export/1`; files are UTF-8 gzip JSON Lines plus plain `manifest.json`; markers `EXPORT_OK` / `EXPORT_FAILED` are written last.
- Keys and units (architecture §5): item key `${registryName}@${meta}` (+ `#${first 12 hex of sha1(SNBT)}` for NBT variants), never meta 32767; fluid key `fluid:${name}`; chances 0..1; fluids in litres; EU/t and ticks; tiers 0..14 with `V[t] = 8·4^t` (t ≤ 13), `V[14] = 2147483640`; recipe id = first 16 hex of sha1 over canonical JSON.
- Commits use a conventional prefix and the message ends with the line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **An export that fails, hangs or is interrupted** (Ctrl-C, a Java crash, no marker after 15 minutes, a JVM that lingers after `EXPORT_OK`, a second `npm run export` while one runs): no orphan Java process keeps port 25566 or CPU, the previously active export stays active, and the half-written `data/export/<id>/` is never activated. Tests: Task 15 "kills the whole process group on timeout", "kills a JVM that lingers after EXPORT_OK and still succeeds", "stops the JVM when aborted", "refuses a second export while the lock is held"; Task 16 "keeps the previous active export when the run fails".
2. **The live server running during an export** (it holds port 25565 and writes `World/` and `logs/` all the time): nothing in the live folder changes, the clone has no world, backups, logs or player files, the clone binds only 127.0.0.1:25566, and a busy 25566 stops the run before Java starts. Tests: Task 14 "leaves the source folder unchanged", "never copies World, backups, logs or player files", "refuses a target outside .local"; Task 15 "rejects a busy port".
3. **A pack update and re-export** (2.9.0 final renames a map, reorders lines, adds a dimension): ids of unchanged recipes stay the same, renamed maps normalize to one id, a new ore dimension that the tier table does not know is reported in `pack.warnings` instead of silently counted as reachable, and a stale clone is never reused. Tests: Task 3 "ignores option order, meta key order and owners" and the alias tests; Task 5 "gives the same id to the same recipe when item indices differ between exports"; Task 7 "flags an ore dimension the tier table does not know"; Task 14 "replaces a stale clone"; Task 18 re-exports and compares recipe ids.
4. **Odd item data** (wildcard meta 32767 without known variants, NBT variants, items whose English name failed, a recipe that points past the items file, a truncated `.gz`, a file shorter than the manifest says): no key ever contains `@32767`, `nameOf` never returns an empty string, and structural damage fails with the file name and line instead of a half-loaded pack. Tests: Task 4 and Task 5.
5. **Derived recipes that would blow up a machine**: the GT microwave explodes on metal or explosive input and sets flammable input on fire, so a microwave recipe is derived only where GT's own lookup returned a real output (the exporter writes `mw` only then). Tests: Task 6 "derives microwave recipes only where the export recorded a safe output"; Task 17 checks a metal dust has no microwave recipe in the real export.

**Not in this plan:** other mods' own recipe registries (Thaumcraft, Avaritia, Botania, Forestry, …; export-mod.md §4.8 calls them an optional second phase) — each can later be one more `ExportSection` (Task 9) plus a converter next to `recipes.ts`. Icons and textures are Plan 3; reading the world is Plan 4.

## Conventions for every task

- Run TypeScript tests with `npx vitest run <file>`; the whole suite with `npm test` (runs `tsc -b` first). "Expected: PASS" means vitest prints `Test Files  N passed` and exits 0.
- Java tasks have no unit tests (the code needs a running Minecraft server). Each one is proven by: a `javap` check of every GT/Forge member it uses against the GT dev jar, a clean build, the reobfuscation check `exporter-mod/scripts/check-reobf.sh` (Task 9), and the real run (Task 17). Shell variables used in Java steps:
  ```bash
  # from the repo root; every Java step runs from the repo root
  export GRADLE_USER_HOME="$PWD/.local/gradle-home"
  GTDEV=$(find "$GRADLE_USER_HOME/caches/modules-2" -name 'GT5-Unofficial-5.09.54.183-dev.jar' | head -1)
  SL=$(find "$GRADLE_USER_HOME/caches/modules-2" \( -iname 'structurelib-1.4.45*-dev.jar' -o -iname 'structurelib-1.4.45.jar' \) | head -1)
  ```
  Build: `(export GRADLE_USER_HOME="$PWD/.local/gradle-home"; cd exporter-mod && VERSION=0.1.0 ./gradlew assemble)` → `BUILD SUCCESSFUL`. Never install the `-dev` jar.
- Java code: Java 8 APIs only (`--release 8`), no lambdas that capture Minecraft classes in static initializers, every per-element read wrapped in `try { … } catch (Throwable t) { ctx.warn(…) }` so one bad machine, item or recipe never aborts a section.
- Non-GT mod classes that are not on the compile classpath (Galacticraft `micdoodle8.*`, GalaxySpace, AmunRa) are reached only through `Reflect` (Task 13); Minecraft and Forge members are always called directly so reobfuscation renames them.

| Rule | Meaning |
|---|---|
| Item index | `i` = 0-based line position in `items.jsonl.gz`; every index used in any file exists there |
| `m == 32767` | wildcard (only from ore-dictionary lists or recipe stacks with wildcard damage); never a real variant |
| Item slot | `null` keeps the slot position; amount `0` = not consumed; chance on GT's 1/10000 scale, omitted when 10000 |
| Fluid slot | litres; chance as for items |
| `inAlt[i]`, `finAlt[i]` | alternatives for slot `i` of `in`/`fin`; `null` or `[]` = none |
| `meta` | every GT metadata entry by identifier; `ItemStack` values as `{ "item": index }`, other non-primitive values as `String.valueOf` |
| Dimension names | GT ore-gen names exactly as GT stores them (`Overworld`, `The End`, `EndAsteroid`, `moon`, `Underdark`); the loader normalizes |
| Material keys | `gt:` / `bw:` / `gtpp:` + `IOreMaterial.getInternalName()` |
| Structure coordinates | canonical orientation (controller front faces north, −z); x east, y up, z south; origin = min corner of blocks ∪ air cells, so every coordinate is ≥ 0 |
| Furnace `ef` / `mw` | output GT's own electric furnace / microwave lookup returned for that input; `mw` is omitted when the microwave would explode, burn or reject it |
| Markers | `EXPORT_OK` or `EXPORT_FAILED` is written after every other file is closed |

Worldgen rules:
- **Dimensions.** One `DimensionInfo` per dimension line: `key = dimKey(name)`, `id`, `name = display || name`, `mod = mod ?? 'unknown'`. The celestial body is the celestial line named by the line's `body` (the exporter sets `body` only for Galacticraft space providers, so the Overworld stays a plain dimension). `kind`: `endasteroid` → `region` (with the id of `theend`, name `Far End Asteroids`, mod `gregtech`); body kind `planet`/`moon` → same; `ore.type === 'Asteroid'` → `asteroids`; else `dimension`. `rocketTier` = body tier when the body is `reachable` and tier > 0. Each celestial `satellite` adds a station: `key = 'station:' + dimKey(parent)`, `id null`, `kind 'station'`, `rocketTier = tier`, `name = display || name`, `mod 'Galacticraft'`. `defaultTier = TIER_DEFAULTS[key]?.tier ?? (rocketTier ? ROCKET_TIER_DEFAULT[rocketTier] : UNKNOWN_DIM_TIER)`; when the key is not in the table and the dimension has `ore` or a `rocketTier`, warn `dimension <key> (<name>) is not in the tier table; assuming <tierName> (<tier>)`. First key wins on duplicates.
- **Veins.** `OreVein { name, dims: dims.map(dimKey), materials: names of the four keys, weight, minY: min of yByDim lows, maxY: max of highs, size, density, kind: 'vein' }`; small ores → `{ name, dims, all four materials = material, weight: amount, minY: y[0], maxY: y[1], size: 0, density: 0, kind: 'small' }`. Material keys become names through `nameOfKey` (unknown → part after `:` + warning).
- **Fluid sources** (one `FluidSource` per kind + fluid + minTier, dims united in first-seen order): `underground` from each config entry's fluids, dims = keys of the dimensions with those ids, minTier 2; `air_intake` from each dimension's `airIntake`, dims = every key sharing that id, minTier 0; `gas_siphon` per depth fluid, dims `['station:' + dimKey(planet)]`, minTier = that station's `TIER_DEFAULTS` tier (else `ROCKET_TIER_DEFAULT[tier]`); `space_pump` per entry, dims `[]` (needs no dimension), minTier 9.
- **Capabilities.** Per void-miner line: `underdark` → `{ key: 'deep_dark_void_miner', name: 'Void miner in the Deep Dark', minTier: 11, dim: 'underdark' }`, other dims → `{ key: 'void_miner:' + key, name: 'Void miner on ' + dimension name, minTier: 6, dim: key }`; `yields` = sorted unique material names of the drop and extra items (an item's `gt.material`, else the material whose `parts` contain it; unmatched items are skipped with one warning per line). Space Elevator mining, when asteroids exist: `space_elevator_mining` (MK-I, minTier 8, asteroids with `moduleTier <= 1`), `space_elevator_mining_mk2` (9, ≤ 2), `space_elevator_mining_mk3` (10, ≤ 3), yields from the asteroid outputs. Always `{ key: 'low_gravity', name: 'Low-gravity processing (space station)', minTier: 3, dim: 'station:overworld', yields: [] }`. A capability without `dim` needs no dimension.
- **Byproducts.** `byproducts[name] = material.oreByproducts` for every material that has `parts.ore` or appears in a vein or small ore.

Search rules (`searchPack`): lower-case and collapse whitespace; tokens starting with `@` filter by registry namespace (items only), tokens starting with `$` filter by an ore name containing the rest; no text tokens and no filters → `[]`. With text `q` (the remaining tokens joined): tier 0 name equals `q`, 1 name starts with `q`, 2 a word of the name (after start, space, `(`, `-`, `/`) starts with `q`, 3 name contains `q`; otherwise every token must match its own way — word start 2, contains 3, an ore name equal 4, an ore name contains 5, the key contains 6 — and the hit's tier is the worst token's. Sort: tier, then `produced` first, then shorter name, then `localeCompare` of names, then key. `produced = pack.producers.has(key)`. Precompute lower-case fields once per pack (`WeakMap<Pack, …>`).

With `--find`: take the first search hit and print `<name>  <key>`, then `<n> producing recipes:` and up to `--limit` (default 20) lines `  - <map name> · <machine names, max 3, then "+N more", or "(no machine)"> · <eut> EU/t · <dur> t (<dur/20 with 1 decimal> s) · <tierName(recipeTier(eut, amps)) or "—" when eut is 0>  |  <inputs> → <outputs>`, then `  … and <k> more` when cut.
