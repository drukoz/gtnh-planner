# Line Layout & 3D Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Place the planned line in the group's world — a clear site near the base and its tap-ins, a compact arrangement for the project's logistics mode, power and logistics hookups that never overvolt a machine or overload a cable, numbered pins, build steps and a power-fit verdict — and show that one layout on the map and in a textured 3D view.

**Architecture:** A pure server module `src/server/layout/` turns `(Pack, Plan, WorldScan, Project)` plus voxels read through Plan 4's `readArea` into one `Layout` (architecture §6.7): site finder → arrangement per logistics mode → A* hookups with cable and transformer choice → pins, parts list, build steps and power fit. A layout service caches the result by plan settings hash + scan id + placement and serves `GET /api/projects/:id/layout`; the SSE `plan` event already means "plan and layout may have changed". The client draws the same `Layout` as a map overlay with numbered pins and drag-to-move placement, and in a three.js `View3D` tab (one `DataArrayTexture` of block faces, one `InstancedMesh` per block shape, OrbitControls, layer slider, hover label, click panel, ghost blocks, block list). The plan route stays Plan 2's, but a small hook lets the layout fill `Plan.power.fits`/`suggestions`, add its parts to the build list and put its pin-linked steps into the build steps (Architecture change requests 1–4).

**Tech Stack:** TypeScript 6.0.3 on Node 24 (type stripping), React 19.3.0, three 0.186.1 (+ @types/three 0.186.0), vitest 5.0.3, @playwright/test 1.63.0.

**Spec:** `docs/superpowers/specs/2026-10-17-gtnh-planner-design.md` (§3.5, §3.6, §3.7, §3.8, §3.10). ## Global Constraints

- Node `>=24.10.0 <25`; TypeScript erasable syntax only (no `enum`, `namespace`, parameter properties, decorators, `<T>x`); relative imports name the real `.ts`/`.tsx` file; type-only imports use `import type`; enums are `as const` objects.
- Dependencies: only architecture §4 pins. This plan uses `three@0.186.1` and `@types/three@0.186.0`; if missing, `npm install --save-exact --before="$(date -v-14d +%F)" three@0.186.1 @types/three@0.186.0` and commit `package-lock.json`. OrbitControls is imported from `three/addons/controls/OrbitControls.js` (same package). No other new dependency.
- Never touch the live server (architecture §2.1, spec §4): the layout only reads voxels through Plan 4's read-only `readArea`; nothing here writes to a world or server folder.
- Tests use synthetic fixtures built by `tests/helpers/` (architecture §10); checks against a real export or world run only with `GTNH_LOCAL=1`.
- Coordinates are world block coordinates `[x, y, z]` + `dim`. `Layout.origin` is the minimum corner of the line's bounding box; `Layout.size` is `[W (x), H (y), L (z)]`; `Project.placement.origin` names the same corner.
- Facing numbers are ForgeDirection: down 0, up 1, north 2 (−z), south 3 (+z), west 4 (−x), east 5 (+x). Rotation is clockwise seen from above: 90° turns north → east → south → west.
- Never overvolt (spec §3.5, gt-mechanics §3.4): every powered block a layout places receives packets of at most `V[its tier]` volts, where arriving volts = source volts − Σ `cable.lossPerBlock` along the path.
- Never overload a cable (gt-mechanics §3.3): every cable run has `voltage ≥` the packet volts it carries and `amps ≥` Σ `ceil(euPerTick / V[tier])` over the machines it feeds (plus the transformer banks' input amps); when no cable in the pack is big enough, the layout says how many parallel runs to lay (`cable_amps`), and runs that lose more than 10 % of their volts are flagged (`cable_loss_high`).
- Transformers (gt-mechanics §3.6): a placed transformer is in step-down mode, takes `V[t+1]` on its front face only (≤ 2 A in) and gives `V[t]` on its five other faces (≤ 4 A out); every emitter hop costs `2^max(0, t−1)` EU per amp (gt-mechanics §3.2).
- Power fit (spec §3.5 "my call"): `yes` when `spareEUt ≥ need` and `storedEU ≥ need × 20 × rainOutageSeconds`; `tight` when only the first holds; `no` otherwise; `need` = the line's average EU/t + cable loss + transformer loss. Generators are suggested in text and as optional parts, never placed.
- Multiblocks use their exported `Machine.structure` size and keep its `air` cells empty (gt-mechanics §5.3).
- Logistics mode comes from `project.settings.logistics` (`direct` default, `routed`, `ae2`); a layout never silently assumes a network or storage the scan did not find (spec §5).
- Determinism: the same inputs give byte-identical `Layout` JSON (fixed sort orders and tie-breaks), so map, 3D view, block list and cache agree (spec §3.8 "they always agree").
- 3D (web-stack §8): three.js `WebGLRenderer` with a `ShaderMaterial` sampling a `DataArrayTexture` through `sampler2DArray` — never `glslVersion: THREE.GLSL3`; V flipped in the shader; `NearestFilter`, no mipmaps, `SRGBColorSpace`; render on demand (no animation loop, the host also runs the game); the 3D tab is lazy-loaded. Textures come from `POST /api/assets/blocks`, `POST /api/assets/icons` and `GET /api/assets/file/<path>`; a face that cannot be resolved is a plain colour (spec §3.8).
- Bounded work on the server: the site search reads at most a `MAX_SITE_SPAN` (192) block square around the base, and every A* search stops after `MAX_PATH_NODES` (200,000) expansions.
- Commits use a conventional prefix and the message ends with the line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A project with no target, no world scan or no base yet** (a friend planning before anyone uploaded a world): `GET /api/projects/:id/layout` still answers 200 with a layout at a default origin, no hookups and a warning that says to pick a scan; the map and 3D tabs show that warning instead of crashing. Tests: Task 11 "lays out without a scan", Task 12 route test.
2. **No clear space near the base** (dense base, a lake, lava, a hillside): nothing is placed into existing blocks silently; the layout takes the best fallback spot outside the base box and adds warning `site_not_clear` plus a `warning` pin with the number of blocks in the way. Tests: Task 4 "treats water and lava as unbuildable", "falls back outside the base when nothing fits", "never builds on scanned blocks or GT machines".
3. **Power the base cannot deliver safely**: no power network, only a lower voltage than the line's machines, or a tap with too few free amps — never a connection above a machine's tier; warning `power_tier_low` / `no_power_tap` / `power_amps_low` and generator suggestions. Tests: Task 3 "says so when the base has no power network", Task 6 "wires a machine above the supply tier to the supply run and warns", Task 9 "warns when the tap has too few free amps".
4. **A hookup path that is blocked or far away** (walls, a tap 200 blocks off): the path search stops within its node budget and returns a straight dashed fallback with warning `no_path`, without stalling the server. Tests: Task 2 "gives up within its node budget", Task 9 "falls back to a straight dashed guide when no route exists".
5. **A dragged placement that overlaps the base, sits underground or above the build limit**: x and z are kept, y is clamped to `1 … 256 − H`, and warning `placement_blocked` reports how many solid blocks are in the way. Tests: Task 4 "checks a user placement", Task 11 "honours a dragged placement and says what is in the way".

## How a layout is built (read once; every task refers to it)

`layoutLine` runs these stages; each task owns one.

1. **Context** (Task 11): base = `findBase(scan, project.world.baseId)`; `ctx = contextFromScan(scan, pack, baseId)`; choose the power network and the logistics network (Task 9).
2. **Units** (Task 5): one unit per *new* machine (`count − owned`) of every placed step; multiblocks take their exported `structure` and get hatch cells.
3. **Placement** (Task 5): a local grid (x = along the line, z = across, y = up). Two rows of units face a one-block **spine** (z = `spineZ`, y = 0); x = 0 … `headWidth − 1` is the **power head** (cable runs and transformer banks); x = `tailX` is the **tail** (chests, request pipe, fluid roots). Row N fronts face south, row S fronts face north.
4. **Mode** (Tasks 7–8): what sits on the spine and the tail — a shared GT item pipe (direct), Project Red routed pipes (routed) or ME cable with interfaces (AE2).
5. **Internal routing** (Task 6): power head + cable trees from each tier's run to every unit, GT fluid-pipe trees per fluid; all with the A* router (Task 2).
6. **Site** (Task 4): the local box (W × H × L) is placed in the world — searched near the base and the taps, or taken from `project.placement`.
7. **Hookups** (Task 9): A* over the world voxels from the chosen taps to the line's power head and logistics port; ghosts of the existing blocks touched.
8. **Pins, parts, steps, power fit** (Tasks 10, 3): numbered pins, the parts list, build steps linked to pins, `fits`/`suggestions`.

```
 local z ↓   x →   0      1 … (units) …            tailX
 0  lane        [run]   ·  ·  ·  ·  ·  ·  ·          ·
 1  row N       [run]  [M][M][M][M][M]               [in chest]
 2  spine       [run]  [=][=][=][=][=][=][=][=][=]   [port]
 3  row S       [run]  [M][M][M][M]                  [out chest]
 4  lane        [run]   ·  ·  ·  ·  ·  ·  ·          ·
```

- Produces (`src/server/layout/path.ts`):
  ```ts
  export const MAX_PATH_NODES = 200_000;
  export interface PathBounds { min: Vec3; max: Vec3 }                     // inclusive
  export interface PathOptions { passable(p: Vec3): boolean; bounds: PathBounds; maxNodes?: number /* MAX_PATH_NODES */; verticalCost?: number /* 2 */; turnCost?: number /* 0.25 */ }
  export interface PathResult { found: boolean; path: Vec3[] /* start … goal, inclusive; [] when not found */; expanded: number }
  export function findPath(starts: readonly Vec3[], goals: readonly Vec3[], opts: PathOptions): PathResult;
  export interface TreeResult { cells: Vec3[] /* new cells in the order added */; links: Array<[Vec3, Vec3]>; unreached: Vec3[] }
  export function growTree(roots: readonly Vec3[], terminals: readonly Vec3[], opts: PathOptions): TreeResult;
  export function straightPath(from: Vec3, to: Vec3): Vec3[];             // x first, then z, then y; inclusive
  export function linkBits(links: ReadonlyArray<[Vec3, Vec3]>): Map<string, number>;   // posKey → bits 1 << side
  ```

Rules (the search must be deterministic, because the map, the 3D view and the cache must agree):
- `findPath` is a multi-source, multi-goal A*. A state is `(cell, side of the move that entered it)`; starts have no side. A cell may be entered when it is inside `bounds` and `passable(cell)` is true **or** it is a goal. Move cost = 1 horizontally, `verticalCost` for sides 0/1, plus `turnCost` when the side differs from the previous move's side. Heuristic = distance to the goals' bounding box (`dx + dz + verticalCost·dy`, admissible). The open list is a binary heap ordered by `(f, h, insertion number)`; neighbours are pushed in `DIRS` order. Each pop counts as one expansion; once `expanded > maxNodes` the search stops with `found: false`. A start that is a goal returns `[start]`.
- `growTree` keeps a set of tree cells (initially `roots`). Terminals are handled in order of (Manhattan distance to the nearest root, `posKey`). A terminal already in the tree is skipped; one that is not `passable` is unreached. Otherwise `findPath([terminal], treeCells, { …opts, passable: p => opts.passable(p) && !inTree(p) })`; on success every path cell except the last (an existing tree cell) is added to the tree and to `cells`, and each consecutive pair of the path becomes a link; on failure the terminal goes to `unreached`.
- `linkBits` sets, for every link `[a, b]`, `1 << sideToward(a, b)` on `a` and the opposite bit on `b`.

- `transformerStages` (step-down only, gt-mechanics §3.6): groups above `supplyTier` go to `under` (fed the supply voltage; Task 6 warns). `need[t]` starts as the amps of the group at tier t; for k from the lowest group tier up to `supplyTier − 1` with `need[k] > 0`: `ampsOut = need[k]`; `ampsIn = ceil(ampsOut × (V[k] + 2^max(0, k−1)) / V[k+1])` (emitter loss, gt-mechanics §3.2); `count = max(ceil(ampsOut / 4), ceil(ampsIn / 2))` (4 A out, 2 A in per transformer); `need[k+1] += ampsIn`; `lossEUt += ampsOut × 2^max(0, k−1)`. `supplyAmps = need[supplyTier] + Σ` over `under` machines of `ceil(euPerTick / V[supplyTier])`.
- `fitPower` (spec §3.5, Global Constraints): `need = power.averageEUt + extraLossEUt`. With `ctx.power`: `rainNeed = need × 20 × rainOutageSeconds`; `fits = spareEUt ≥ need ? (storedEU ≥ rainNeed ? Without `ctx.power`: `no`, `"No power network found at this base; the line needs <need> EU/t on average"`, generator text for `need` at `input.tier`. All numbers through `fmtInt`.
- `generatorSuggestion(pack, S, T)`: turbine = lowest-`mteId` `kind 'turbine'` with tier T; none → `"Add generators for about <S> EU/t at <TIER>"`, no lines. Turbines `nT = ceil(S / V[T])`.   export const SITE_CLEARANCE = 1;      // free ring around the line
  ```ts
  export const MAX_STEP = 1;            // a column may sit 1 above or below the floor (dug or filled)
  export const MAX_SITE_SPAN = 192;     // x/z span of the voxel read (stays far below MAX_AREA_VOXELS)
  export const SITE_HEADROOM = 8;
  export interface Footprint { w: number; h: number; l: number }            // local W (x), H, L (z), before rotation
  export interface SiteRequest {
    dim: number; footprint: Footprint; base: Base; baseFloorY: number;
    ports: { power?: Vec3; logistics?: Vec3 };                             // local cells, may lie outside the box
    taps: { power?: Vec3; logistics?: Vec3 };                              // world positions
    avoid: ReadonlySet<string>;                                            // posKeys of every scanned machine, pipe, storage and logistics block
  }
  export interface Site { origin: Vec3; rotation: Rotation; size: Vec3 /* world */; floorY: number; dig: number; fill: number; blocked: number; unsupported: number; score: number; reason: 'search' | 'placement' | 'fallback'; moved: boolean }

  export function isFluidBlock(ref: BlockRef): boolean;
  export function baseFloorY(scan: WorldScan, base: Base): number;
  export function siteSearchBox(base: Base, floorY: number, footprint: Footprint, taps: readonly Vec3[]): BBox;
  export function findSite(req: SiteRequest, vox: Voxels): Site | null;     // null = nothing clear and flat enough
  export function fallbackSite(req: SiteRequest, vox: Voxels | null): Site;
  export function checkPlacement(req: SiteRequest, vox: Voxels | null, placement: { origin: Vec3; rotation: Rotation }): Site;
  ```

Rules:
- Replaceable (counts as air): `minecraft:air`, `tallgrass`, `double_plant`, `red_flower`, `yellow_flower`, `deadbush`, `snow_layer`, `vine`, `fire`, `brown_mushroom`, `red_mushroom`. Fluid: `minecraft:water`, `flowing_water`, `lava`, `flowing_lava`, or any id matching `/fluid/i`.
- Column top: scanning down from the top of the voxel box, the first cell that is neither air nor replaceable. The column is **ground** when that cell is known (not `UNKNOWN_INDEX`), not a fluid, has no `mteId`, and its posKey is not in `avoid`. Columns with no such cell, unknown cells, fluids, GT tiles or scanned blocks are never ground.
- `baseFloorY`: the most common `pos[1]` of `scan.machines` with `baseId === base.id` (ties → lower), else `base.center[1]`.
- `siteSearchBox`: x/z = the base box ± `SITE_MARGIN`, grown to include every tap ± 2; y = `[floorY − 1 − SITE_HEADROOM, floorY + footprint.h + SITE_HEADROOM]` grown to every tap y ± 2, clamped to 0…255; an x or z span above `MAX_SITE_SPAN` becomes `[center − 96, center + 95]` around the base centre (taps outside it are reached by the straight fallback in Task 9).
- `findSite` tries every rotation for every `(x0, z0)` whose rectangle (rotated W × L) plus the clearance ring lies inside the voxel box. A rectangle is valid when all its columns are ground, `y0` = their most common top height (ties → lower) and every column is within `MAX_STEP` of `y0`, every ring column is ground with top ≤ `y0 + MAX_STEP`, and `y0 + footprint.h ≤` the box's max y. `origin = [x0, y0 + 1, z0]`; `dig` / `fill` = Σ of tops above / below `y0`. Score (lower wins) = `2 × manhattan(centre, base.center) + manhattan(power port, power tap) + manhattan(logistics port, logistics tap) + 4 × |origin.y − baseFloorY| + 2 × (dig + fill)`, where `centre = [x0 + floor(W'/2), origin.y, z0 + floor(L'/2)]`, ports go through `toWorld(port, origin, rotation, [w, h, l])` and a term is 0 when its port or tap is missing. Iterate `x0` ascending, then `z0`, then rotations `0, 90, 180, 270`, keeping only strictly better scores, so ties go to the lowest x, then z, then rotation.
- `checkPlacement`: x and z from the placement, `y` clamped to `1 … 256 − footprint.h` (`moved` when clamped), the given rotation; `blocked` = known cells inside the line's volume that are neither air nor replaceable (fluids count); `unsupported` = rectangle columns whose cell at `y − 1` is known and air, replaceable or fluid; `dig`/`fill` against floor `y − 1`; `score 0`. With `vox === null` every count is 0.
- `fallbackSite` (spec §3.6, Review Focus 2: never placed into blocks silently): rotation 0, `origin = [base.bbox.maxX + 1 + SITE_CLEARANCE, baseFloorY, base.center[2] − floor(l / 2)]`, counts as in `checkPlacement`, `reason 'fallback'`.

Rules:
- `stepDepths`: 0 for a step fed only by `raw` (or with no flows), else 1 + the deepest step feeding it; flows that close a loop are ignored (depth-first with an "in progress" set).
- `unitsFromPlan`: steps that are `handCraft`, have `machine.mteId < 0`, or `count − owned ≤ 0` are skipped; a machine missing from `pack.machines` is skipped with `{ code: 'unknown_machine', stepId, text: '<name> (#<mteId>) is not in this recipe export' }`; a `steam` machine gets `electric: false` and `{ code: 'steam_machine', stepId, text: '<name> runs on steam: connect a steam supply by hand' }`. Units are sorted by (depth, step id, index); `tier = step.machine.tier`, `euPerTick = step.euPerTick`.
- A singleblock is `size [1, 1, 1]` with one `machine` cell (`machineRef(m)`, label `m.name`, item `m.itemKey`).
- A multiblock uses `structure` (Plan 1 canonical frame): the controller cell is `machine`, other cells with an `mteId` are `hatch` (named from `pack.machines`), the rest `casing` (label = item name of `itemKey(id, meta)`, else the block id; item = that key). Missing or `truncated` structure → a 3×3×3 box of `UNKNOWN_BLOCK` casings with the controller at `[1, 0, 0]` and warning `{ code: 'structure_unknown', stepId, text: '<name>: no exported structure, drawn as a 3×3×3 box — check its real size in game' }`.
- Hatch cells (they replace casings; gt-mechanics §5 — hatch positions are not in the export): bottom-layer candidates = `casing` cells at y = 0 holding the layer's most common `id@meta` (ties → smallest string). Front candidates = candidates with the smallest z of block cells in their column; back = the largest z. Front, ordered by `(|x − controller.x|, x)`: `input_bus` (if `io.itemIn`), `output_bus` (if `io.itemOut`). Back, ordered by `(|x − floor((W−1)/2)|, x)`: `energy` (if electric; tier = step tier), then `maintenance` (falls back to any remaining bottom candidate). Fluid hatches on the top layer (y = H − 1), candidates = that layer's most common casing, ordered by `(z, x)`: one `input_hatch` per `io.fluidIn` key, then one `output_hatch` per `io.fluidOut` key. Buses and fluid hatches use `pickHatch(…, null)`, energy `pickHatch('MTEHatchEnergy', tier)`. Not enough cells or a missing hatch machine → `{ code: 'hatch_cells_short', stepId, text: '<name>: put the remaining hatches (<kinds>) on any casing' }`.
- `placeUnits`: cursors `cN = cS = headWidth`; each unit goes to row N when `cN ≤ cS`, else S; `x = cursor + (row not empty and (unit or the row's previous unit is a multiblock) ? 1 : 0)`; then, while any of its item-port spine cells is within `portSpacing − 1` of a cell already claimed (spacing 1: never the same cell; 2: never the same or a neighbouring cell), `x += 1`; cursor = `x + W`. `dN`/`dS` = deepest unit per row (0 when empty); `spineZ = 1 + dN`; `L = dN + dS + 3`; `tailX = max(cN, cS)`; `W = tailX + 1`; `H` = tallest unit. Row S units keep the canonical orientation (`at = [x, 0, spineZ + 1]`, cell `at + c`); row N units turn 180° (`at = [x, 0, spineZ − D]`, cell `at + (W−1−cx, cy, D−1−cz)`). Machine blocks face the spine (3 in row N, 2 in row S); bus hatches face the spine, energy and maintenance hatches face away, fluid hatches face up (1). Air cells go to `reserved`.
- Ports (local): singleblock `power` = the cell behind it (away from the spine; `null` when not electric), `items` = `[spine cell in front]`, `fluidIn`/`fluidOut` = `[cell above]` when it has fluid inputs/outputs, `itemFaces` = the machine's front when `io.itemOut`, `fluidFaces` = its top (side 1) when it has fluid outputs. Multiblock: `power` = the cell behind the energy hatch; `items` = the cells in front of the input/output buses when those are spine cells; fluid ports = the cells above the fluid hatches; `itemFaces` = the output bus's spine-facing side; `fluidFaces` = output hatches' tops.

Rules (spec §3.5 never overvolt, §3.6 shared runs; gt-mechanics §3.3, §3.6):
- Runs: for the supply tier and every stage's `toTier`, a straight cable column at `x = runX(supply, tier)`, y = 0, z = 0 … L − 1. Run cable = `pickCable({ volts: V[tier], amps })` with `amps = supplyAmps` for the supply run and the stage's `ampsOut` below; `ampsShort` → `{ code: 'cable_amps', text: 'No cable carries <A> A at <TIER>: run <n> parallel <cable> lines' }` with `n = ceil(A / cable.amps)`.
- Banks: stage `from → to` puts `count` transformers (`pickTransformer(pack, to)`) at `x = runX(supply, to) − 1`, y = 0, z = `spineZ − floor(count/2) + j`, facing west (4): the front (step-down input) touches the higher run, the east face feeds the lower run. More transformers than `L` → the rest are left out with `{ code: 'transformer_bank', text: 'Put <n> more <name> beside the bank' }`; no transformer for that tier → `{ code: 'no_transformer', text: 'No <TIER> transformer in this export' }`.
- While one feed tier is routed, the power ports of units on other feed tiers are not passable (so a higher-tier run never takes a lower-tier machine's port cell).
- Each electric unit is fed from the run of `feedTier = min(unit.tier, supply)`; a unit above the supply tier gets `{ code: 'power_tier_low', stepId, text: '<names> need(s) <TIER> power but the line gets <SUPPLY>: it will run short — add a step-up transformer or a generator at <TIER>' }` (one warning per unit tier; under-voltage never damages a machine, gt-mechanics §3.5, so it is wired, not left out). For each feed tier (descending): `growTree(run cells, the units' power ports sorted by x, y, z, …)` with `passable` = inside `{min [0,0,0], max [W−1, H, L−1]}` (H = placement height, so runs may pass over singleblocks) and not occupied by placement blocks, `input.occupied`, reserved air cells, head blocks or earlier routed cells. Tree cells become `cable` blocks with the run's cable. Unreached → `{ code: 'route_failed', stepId, text: 'Could not wire <name> inside the line — connect it by hand' }`.
- Connections (`linkBits`): run cells link along z; tree links as returned; each port cell links to the block it powers; each transformer links to both runs. A cable never links to a run of another tier, so no machine ever receives more than `V[its tier]`.
- `fluidNets`: one net per fluid key in any placed unit's `io`; producers/consumers = units' `fluidOut`/`fluidIn` ports for that key; `atTail` when a plan flow of that key comes from `raw` or goes to `out`/`sink`, or touches a step with no placed unit; `litresPerSecond` = Σ `perSecond` of the flows of that key; `faces` = producers' `fluidFaces`.
- Fluid trees (after power): root = `[tailX, tailFluidY + i, spineZ]` for the i-th `atTail` net (key order), else the first producer port (x, y, z order). `growTree([root], other ports)`; the root and new cells are `pipe` blocks (`pickFluidPipe(rate)`, label `<pipe name> (<fluid name>)`), port cells link down to their machine; a pump cover (`role 'cover'`, `parts.pump_cover`, label `Electric Pump (LV) cover`, facing = side) on every face in `faces`. No fluid pipe in the pack → `{ code: 'no_pipe', text: 'No GT fluid pipe in this export: connect <fluid> by hand' }`; unreached port → `route_failed` `'Could not lay the <fluid> pipe to <name> — connect it by hand'`.

Rules (spec §3.7 numbered pins, §3.10 build steps linked to pins):
- `findReuse`: for each plan step with `owned > 0` (by step id), `positions` = the scan's machines with that `mteId` in the base (`baseId === base.id`, same dim), nearest to `near` first (ties posKey), at most `owned`; `count = step.owned` (the planner's decision); `name` from `pack.machines`; steps with no match are skipped (the planner may count owned machines elsewhere).
- `makePins`: numbers from 1 in the order site, power, logistics, reuse (one pin each, at `positions[0]`, text `Reuse your <count>× <name>`), warnings (by code, then posKey). Every pin has `dim`.
- `layoutSteps` — ids are stable so ticks survive re-plans; `order` = index + 1; `pin` = `pinNumber(pins, …)` (undefined without pins):
  1. `layout:site` (place, site pin): `Clear a <W>×<L> spot[ at pin <n>] (<H> high) and keep a 1-block path around it` + `; dig <dig> and fill <fill> blocks to level it` when either is > 0.
  2. `layout:roof` (place, site): `Roof the line: GT machines left in the rain can catch fire or explode` (gt-mechanics §3.4).
  3. `layout:place:<stepId>` (place, site) per placed step in unit order: singleblock `Place <n>× <name> facing the middle row`; multiblock `Build <n>× <name> (<W>×<H>×<D>) with the controller facing the middle row; hatches: <labels>` (the first unit's hatch labels in the order input bus, output bus, energy, maintenance, input hatches, output hatches).
  4. `layout:power:stage:<toTier>` (power, power pin) per stage from the supply down: `Place <count>× <transformer> between the <FROM> and <TO> cables, front (input) toward <FROM>`.
  5. `layout:power:wire:<tier>` (power, site) per cable entry: `Wire the <TIER> machines with <cable> (<cells> blocks)`.
  6. `layout:power:hookup` (power, power pin) when `supplyTier !== null`: with `power`: `Run <blocks>× <cable> from the tap[ at pin <n>] to the line: up to <amps> A at <TIER>, arriving at <volts> V`; without: `No power network found: feed the line from your own <TIER> supply (see the power suggestions)`.
  7. Drafts of kind `logistics`, in order (their `pin` names the pin kind).
  8. `layout:logistics:fluid:<key>` (logistics, site): `Lay <cells>× <pipe> for <fluid>; pump covers on the machines that make it push it out`.
  9. `layout:logistics:hookup` (logistics, logistics pin) when `logistics`: `Connect the line to your <kindName> network[ at pin <n>]: <blocks>× <part>`.
  10. Drafts of kind `configure`, in order.
  11. `layout:reuse:<stepId>` (logistics, that reuse pin): `Hook your <count>× <name>[ at pin <n>] into the line's logistics`.
  12. `layout:test` (test, site): `Switch on and check: every machine has power, none is fed above its tier, items reach the output`.
  Status `empty` → only the reuse steps.
- `bomFromBlocks` (spec §3.10 "every … cable, pipe/cover/interface part"): counts blocks with an `item` and role `cable`, `transformer`, `hatch`, `pipe`, `cover`, `interface`, `chip_pipe`, `chest` (machines and casings are already in Plan 2's build list; ghosts exist already). Why per role: cable → `line wiring` / `power hookup` (when `hookup` is set); transformer → `transformers`; hatch → `hatches (replace casings)`; pipe → `pipes in the line` / `logistics hookup`; cover → `covers`; interface, chip_pipe → `logistics parts` / `logistics hookup`; chest → `chests`. `extra` lines are added to the same keys. Amounts summed, whys de-duplicated, sorted and joined with `; `, lines sorted by key.

`layoutLine` stages (see "How a layout is built"):
1. `mode = project.settings.logistics`; `parts = resolveParts(pack)`. A plan whose `status` is `empty` or `infeasible` → `{ status: 'empty', dim: 0, origin: DEFAULT_ORIGIN, size: [0, 0, 0], rotation: 0, mode, blocks: [], hookups: [], pins: [], buildSteps: [], bom: [], warnings: [] }` (the plan already says why).
2. `base = findBase(scan, project.world.baseId)`. No base → `status 'no-world'`, origin `DEFAULT_ORIGIN`, rotation 0, no pins, no hookups, warning `{ code: 'no_scan', text: 'Pick a world scan and base on the Map tab to place the line' }` when `project.world.scanId` is null, else `{ code: 'no_base', text: 'This scan has no base here to build next to' }`; everything local (units, mode, internal routing, steps without pins) is still built so the 3D view and the parts list work, stages 6, 8 and 9 are skipped, and `power = plan.power` (nothing to compare against, so `fits` stays unset). `ctx = base ? contextFromScan(scan, pack, base.id) : emptyContext()`.
3. Units (Task 5). None → `status 'empty'` with reuse pins and reuse steps only (and `power` from step 8 with no extra loss).
4. Power: `lineTier` = highest electric unit tier; `network = choosePowerNetwork(scan, base, lineTier)`; `supplyTier = network?.voltageTier ?? lineTier`; `stages = transformerStages(tierGroups(electric units), supplyTier)` (null when no electric unit). Logistics network = `chooseLogisticsNetwork(scan, base, mode)`.
5. `placeUnits(units, { headWidth: headWidthFor(stages), portSpacing: PORT_SPACING[mode] })` → `buildMode` → `routeInternal({ …, occupied: [...placement.blocks, ...mode.blocks], fluids: fluidNets(…), tailFluidY })`. Local size = `[W, 1 + highest block y, L]`.
6. Site (Task 4): `avoid` = posKeys of every scanned machine, pipe, storage block and `logisticsBlocks` entry in the base's dimension; `ports.power = [−1, 0, spineZ]` (when there is a power head), `ports.logistics` = the logistics port's first face neighbour outside the box (`DIRS` order); taps for scoring = the network taps nearest the base centre; `vox = await deps.readArea?.(base.dim, siteSearchBox(…))` (a thrown `RangeError` or missing `readArea` → `vox = null` and `{ code: 'terrain_unknown', text: 'The ground around the base could not be read; the line is placed beside the base unchecked' }`). With `project.placement`: `checkPlacement`; `blocked > 0` → `{ code: 'placement_blocked', text: '<n> block(s) are/is in the way at the chosen spot' }`, `moved` → `{ code: 'placement_moved', text: 'Moved the line to y=<y> to stay inside the world height' }`. Without: `findSite` ?? (`fallbackSite` + `{ code: 'site_not_clear', text: 'No clear, flat ground near the base: the line is placed beside it — <blocked> blocks in the way, <unsupported> columns without a floor' }`).
7. Every local block goes to the world with `toWorld`, `rotateFacing`, `rotateConnections`; world size = `rotatedSize`.
8. Hookups (Task 9, only with a base): power when `network` and electric units exist (tap nearest the world power port; ports = the supply run's world cells; `amps = stages.supplyAmps`); logistics when the mode returned a `hookup` and a network exists (ports = `[world logistics port]`). Hookup blocks get `hookup` = their index; `ghostBlocks(vox, pack, [tap.pos], lineCells)` per hookup. No power network but electric units → `{ code: 'no_power_tap', text: 'No power network found at this base' }`. - Plan route (`GET /api/projects/:id/plan`): sends `planFinish ? await planFinish(plan, project) : plan`; when `planFinish` rejects it sends the unfinished plan plus `{ code: 'layout-failed', text: 'The line layout failed: <message>' }`; the plan cache keeps unfinished plans (the layout depends on placement, which is not in the plan key).
- Ops route: a batch containing a `placement` or `clearPlacement` op triggers the same background plan computation and `event: plan` as `settings`/`world` (architecture §7.1: the `plan` event means "plan and layout may have changed — refetch both").

Rules (spec §3.7):
- `overlayShapes` (nothing when `view.dim !== layout.dim`), screen positions from Plan 4's `worldToScreen`:
  - per (x, z) column of line blocks (no `hookup`, not `ghost`, not `cover`): one filled `rect` (`ppb × ppb`) in the colour of the column's top-priority role (machine, hatch, casing, transformer, chest, interface, chip_pipe, pipe, cable), shifted by `drag`;
  - the line box outline (`origin` … `origin + size` in x/z, stroke `#ffffff`, solid), shifted by `drag`;
  - each hookup as a dashed `path` (`[6, 4]`, width 2) through its cell centres — power in `VOLTAGE_COLORS[tap.voltageTier ?? 0]`, logistics in `LOGISTICS_COLORS[routed | ae2 | gtpipe]` by tap kind (`pipe` → `gtpipe`) — "dashed = still to build";
  - one `arrow` (`#ffffff`) per plan flow between two steps that both have machine blocks, from the centre of the first machine of `from` to the first machine of `to` (machine order = layout order) — "arrows for item flow".
- `layoutMarkers`: pins of `layout.dim`, sorted by `n`, `{ n, pos, color: PIN_COLORS[kind], label: 'Pin <n>: <text>' }`.
- `layoutOverlay.onPointer` returns `false` unless `moving`; while moving: `down` inside the line starts a drag (`onDrag({from, to: from})`), `move` updates it, `up` calls `onDrop(draggedOrigin(…))` then `onDrag(null)`; all three return `true` while dragging (the map does not pan). `draw` = `drawShapes(ctx, overlayShapes(layout, view, drag ? { dx, dz } : null, flows))`.
- `createLayoutLoader.request` refetches only when `plan` (by identity — Plan 2's store replaces the object after every `plan` event) or `key` changed, debounced 100 ms; an answer to an older request is dropped; errors set `error` (`ApiError.message`) and keep the previous layout.
- `lineSummary`: `newMachines` = machine blocks; `reused` = Σ `owned` over non-hand-craft plan steps; `footprint` = `<W>×<L>×<H>` (world size x, z, y); `peak` = `<fmtInt(plan.power.peakEUt)> EU/t`; fits `yes` → `Fits`, `tight` → `Tight in rain`, `no` → `Does not fit`, else `Unknown`.
- `LinePanel` (`data-testid="line-panel"`): heading "New line"; `Machines: <n> new, <r> reused`, `Footprint`, `Peak`, `Power: <fits>` with `power.detail` and each suggestion; buttons **Move line** (`aria-pressed`), **Rotate 90°**, **Auto place**; pins as `<li data-testid="pin-<n>">` with a dot in the pin colour and `<n>. <text>`, clicking calls `onPin(n)`; layout warnings as a list. Status `no-world` → `Pick a world scan and base to place the line`; `empty` → `Nothing new to build — every step runs on machines you own`; `loading` → `Laying out the line…`; `error` → the message.
- `MapTab` (Plan 4) gains: `useLayout(project.id, plan, project)`; state `moving` and `drag`; `overlays = [...existing, layoutOverlay(…)]` (last, so it sees pointer events first); `markers = [...noteMarkers(…), ...layoutMarkers(layout)]`; `LinePanel` under the found panel; Move drop → `send([{ op: 'placement', origin, rotation: layout.rotation }])` and leaves move mode; Rotate → `send([{ op: 'placement', ...rotatedPlacement(layout) }])`; Auto place → `send([{ op: 'clearPlacement' }])`; a focused pin (`usePinFocus`) re-centres `MapView` on it (pass it as `focus` and use it in the `key` so the view moves) and highlights its row.
- `StepsView` (Plan 2): a step with `pin` shows `<button class="pin-link" data-pin="<n>">pin <n></button>` that calls `focusPin(n)` and sets `location.hash = '#map'`.

Rules (spec §3.8; web-stack §8 — one `DataArrayTexture`, one `InstancedMesh` per shape):
- `tiles[0]` is always `{ key: 'fallback', layers: [], color: [128, 128, 128] }` (used when the GPU has fewer array layers than tiles). Other tiles are de-duplicated by `JSON.stringify(layers)`, or `color:<r>,<g>,<b>` for solid ones.
- Instances, in block order: `cover` → one `plate` on side `facing ?? 2`, all six tiles = the icon of `itemKey(block.id, block.meta)` (Plan 3 icons; covers and parts are items); `cable`, `pipe`, `chip_pipe` → a `core` plus one `arm` per set bit of `connections` (ascending), tiles = the block's `north` face; every other role → one `cube`, world side s showing `faces[canonicalFaceFor(facing ?? 2, s)]`; `ghost` role → `ghost: true`. A face whose layer list is empty, or a block with no `BlockFaces`, uses a solid tile of `BlockFaces.fallbackColor` when known, else `ROLE_FALLBACK[role]` (machine/hatch/casing/transformer from Plan 3's `KIND_COLORS` basic/hatch/casing/transformer; cable `KIND_COLORS.cable`; pipe `KIND_COLORS.item_pipe`; cover `[220, 220, 220]`; interface `[126, 87, 194]`; chip_pipe `[255, 112, 67]`; chest `[160, 110, 50]`; ghost `[200, 200, 200]`).
- `canonicalFaceFor(facing, s) = rotateFaces(identity, facing)[FACES[s]]` — the inverse view of Plan 3's rotation, so the front shows where the machine faces.
- `visible`: false for ghosts when `!show.ghosts`, for blocks with `hookup` when `!show.hookups`, and for `pos[1] > maxLayer` ("step through layers": the slider shows layers 0 … k).
- `blockList`: non-ghost blocks grouped by label, sorted by count descending then label; hookups as `<Power|Logistics>: <n> block(s) from pin <pin>` (the pin of that kind at the tap's position; `from the tap` when none); `size = '<W>×<L>×<H>'`.
- `pickInfo`: title = label; lines: `Facing <side name>` when `facing` is set; for a block with `stepId` and a plan step: `Makes <amount>× <name>, … from <amount>× <name>, …` (per run, `plan.names[key] ?? key`) and `<TIER> · <euPerTick> EU/t`; covers `Cover on the <side> side`; hookup blocks `Part of the <kind> hookup`; ghosts `Already in your base`.
- `compositeTile`: source-over in order (`out = src·a + dst·(1 − a)`, alpha `a + dstA·(1 − a)`), tint multiplies RGB before blending (Plan 3 drawing rules), channels rounded; `null` when every entry is `null`.

```ts
export const VERTEX_SHADER = `
attribute vec3 aTiles0; attribute vec3 aTiles1; attribute float aLayer;
varying vec2 vUv; flat varying float vTile; varying float vShade; varying float vLayer;
void main() {
  vec3 n = normalize(mat3(instanceMatrix) * normal);
  if (n.y < -0.5) { vTile = aTiles0.x; vShade = 0.5; } else if (n.y > 0.5) { vTile = aTiles0.y; vShade = 1.0; }
  else if (n.z < -0.5) { vTile = aTiles0.z; vShade = 0.8; } else if (n.z > 0.5) { vTile = aTiles1.x; vShade = 0.8; }
  else if (n.x < -0.5) { vTile = aTiles1.y; vShade = 0.6; } else { vTile = aTiles1.z; vShade = 0.6; }
  vUv = uv; vLayer = aLayer;
  gl_Position = projectionMatrix * modelViewMatrix * instanceMatrix * vec4(position, 1.0);
}`;
export const FRAGMENT_SHADER = `
precision highp sampler2DArray;
uniform sampler2DArray uTex; uniform float uMaxLayer; uniform float uAlpha;
varying vec2 vUv; flat varying float vTile; varying float vShade; varying float vLayer;
void main() {
  if (vLayer > uMaxLayer + 0.5) discard;
  vec4 c = texture(uTex, vec3(vUv.x, 1.0 - vUv.y, vTile));
  if (c.a < 0.1) discard;
  gl_FragColor = vec4(c.rgb * vShade, uAlpha);
}`;
```

## Architecture change requests

The tasks above assume each request is granted. All are additive; nothing defined in the architecture is renamed or reshaped.

1. **`planForProject` (Plan 2, `src/server/http/routes/projects.ts`, §7.1).** `export function planForProject(app: AppContext, project: Project): Promise<Plan>` — the existing body of `GET /api/projects/:id/plan` before it sends (context hook, `PlanCache` keyed per §11.8, `scanId` set). *Why:* the layout must use the same cached plan as the plan route instead of planning twice. *Diff:* extract the handler body into this export; the handler calls it.
2. **Plan finishing hook (Plan 2 plan route, §7.1).** `app.services.planFinish?: (plan: Plan, project: Project) => Promise<Plan>`; when set, the plan route sends its result (a rejection sends the unfinished plan plus warning `layout-failed`); the cache keeps unfinished plans. *Why:* Plan 2's `powerSummary` leaves `fits` to Plan 5, and spec §3.5/§3.10 want the power fit, the layout's parts and its pin-linked build steps in the plan the existing views show; all three depend on the placement, which is not in the plan cache key. *Diff:* 4 lines in the plan route.
3. **`plan` event after placement ops (Plan 2 ops route, §8).** A batch containing `placement` or `clearPlacement` triggers the same background re-plan and `event: plan` as `settings` and `world`. *Why:* other tabs must refetch the plan (power fit, steps) and the layout when someone moves the line; §7.1 already defines the `plan` event as "plan and layout may have changed". *Diff:* widen one condition.
4. **`expandBomLines` (Plan 2, `src/server/planner/bom.ts`).** `export function expandBomLines(pack: Pack, lines: BomLine[], settings: PlanSettings, ctx: PlanContext): Promise<{ lines: BomLine[]; totals: BomLine[] }>` — the child expansion `buildBom` already performs, exposed for lines that do not come from plan steps. *Why:* spec §3.10 wants cables, pipes, covers and interfaces broken down to base materials like the machines. *Diff:* extract from `buildBom`, which then calls it.
5. **Layout type additions (§6.7, owned by this plan; listed for visibility).** Optional `LayoutBlock.item`, `LayoutBlock.connections`, `LayoutBlock.hookup`, `Hookup.found`, `Layout.status` (`'ok' | 'empty' | 'no-world'`), `Layout.power`; export `LayoutStatus`; `layoutLine` takes an optional fifth argument `deps?: { readArea?(dim, bbox): Promise<Voxels>; maxPathNodes?: number }` (the §6.7 signature still holds); `src/shared/layout/geometry.ts` is a new shared module (pure, no `node:*`/DOM).
6. **Item-as-block refs for parts (Plan 3, `POST /api/assets/blocks`).** Parts that are items in game (GT covers, Project Red chips, AE2 bus parts) are drawn from their item icon (`POST /api/assets/icons`), so no new block id is needed; Project Red pipes and ME cable use Plan 3's `partBlockRef` / `ae2CableBlockRef`, and the ME interface and chest are real blocks. *Ask:* Plan 3's curated table resolves `appliedenergistics2:tile.BlockInterface@0` and `partBlockRef('pr_rbasic' | 'pr_rinterface' | 'pr_rrequest')`; unresolved ones fall back to plain colours (spec §3.8), so nothing breaks without it.
