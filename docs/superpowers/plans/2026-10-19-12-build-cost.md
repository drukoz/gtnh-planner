# Build Cost, Machine Sharing and Tier Choice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The planner counts the raw material to build every machine a line adds beyond what the group owns, with whole machine counts, one owned machine shared by several steps in networked logistics modes, and a machine tier chosen per step — the user's "least raw materials, also for the machines we do not have", "reuse machines we have" and "disable the reuse for the whole recipe".

**Architecture:** A memoized price table prices every candidate machine (its item's crafting chain; a multiblock adds its structure) with the cost analysis the planner already has. Each step recipe gets its machine options (every eligible tier, overclocked, with build cost and owned count). When build cost counts, a build-cost MIP replaces plan 09's step-charge MIP inside `solveLine`: whole new machines per step and option, owned machines free (pooled per type in networked modes), the step charge kept per step, a node limit plus a time guard with an LP-relaxation fallback; the later stages (base, power, canonical) stay inside the machines it bought. Plan assembly, Make N, the build list, Plan 5's reuse pins and the client follow the chosen counts, tiers and sharing.

**Tech Stack:** Node 24 (type stripping) · TypeScript 6.0.3 · highs 1.15.3 · React 19.3.0 · vitest 5.0.3 · @playwright/test 1.63.0 (no new dependency).

**Spec:** `docs/superpowers/specs/2026-10-17-gtnh-planner-design.md` §3.2 (Make N), §3.3 (Objective, "How materials are counted", "Reusing machines we have"), §3.10; contracts `docs/superpowers/plans/2026-10-17-00-architecture.md` §6.3, §6.4, §11.26–§11.29 and plan 09's §11.31–§11.37; background `docs/research/gt-mechanics.md` §2 (overclocking), `docs/research/prior-art.md` §3.3, §3.6.

3. **A chain whose build MIP hits the time guard**: the plan still comes out, `build-cost-approx`, whole counts rounded up from the relaxation, no stage runs past its machines — Task 4 "falls back to the relaxation rounded up when the time guard stops the MIP".
4. **One owned machine serving three steps on a Project Red line, then the project switched to machine to machine**: shared → one pin, one owned unit, peak power counted once; direct → one step keeps it, the others get new machines; no errors either way — Task 5 "shares one owned assembler between three steps on a network", Task 6 "gives a shared owned machine one pin".

**Pricing rule** (the "same pricing as derived materials", pricing.ts `costModel`): with `s = { ...settings, avoid: [], recipeChoice: {}, routeDerived: true }`, `basis = planBasis(pack, s, ctx)` and `leaf = makeLeafOracle(pack, s, basis.avail, basis.prices)` — no `supplied` option, so water, air, cobblestone and lava stay leaves at 0 (plan 09 Task 3: "build-material breakdowns keep free inputs as leaves"); stop items are leaves at their override or price — `cost(key)` is `leaf(key).cost` for a buyable key, else `analyzeCosts(buildCandidates(pack, s, basis.env, leaf, <the non-buyable keys>)).cost(key)`. **Cache key** (state it in the module doc): `machinePricingKey` = `settingsHash({ ...defaultSettings(), tier: effectiveTier(settings, ctx), coilHeat: settings.coilHeat, dims: settings.dims, excludedCategories: settings.excludedCategories, costOverrides: settings.costOverrides, stopItems: settings.stopItems, expandItems: settings.expandItems })` + `'|'` + `basisContextKey(ctx)`; the memo key is that + `'|'` + the SHA-1 (`node:crypto`) of the sorted, deduplicated `keys` joined by `\n`. So target, amount, mode, logistics, horizon, reuse settings and avoid list never invalidate it, and one machine's price never depends on the batch history (the batch is part of the key). `MACHINE_PRICE_MEMO_SIZE` entries per pack (`WeakMap<Pack, Map>`), least recently used dropped, a failed computation not kept, concurrent callers share one promise (pricing.ts `linePricing` is the pattern). `yieldToEventLoop()` before the graph walk.

**Machines:** `machineBuildCost` is `null` for `undefined`, a pseudo machine (crafting table, hand, furnace) or any part priced Infinity; a singleblock (any non-multiblock) is `sig9(cost(m.itemKey))`; a multiblock is `sig9(cost(m.itemKey) + Σ structureParts amount × cost)`. `structureParts` is bom.ts's (every exported block except the controller cell and blocks of the controller's own mteId, one per cell, keyed by the machine item for GT tile blocks else `itemKey(block.id, block.meta)`), except that a block whose machine is a `hatch` counts as `minimalHatch` of it: the hatch of the same simple class name (`cls` after the last `.`) with the lowest `tier` (no tier sorts last), ties by lowest mteId, cached per pack. (On the real export the EBF's exported structure holds a UV muffler hatch, `hatch.muffler.tier.09`, mte 99; priced as is it would make every EBF unbuildable below UV.) `buildKeys` = each machine's `itemKey` plus, for multiblocks, its structure part keys, sorted and deduplicated. `bomBuildCost` = `max(0, sig9(Σ add amount × cost − Σ minus amount × cost))` over one `itemPrices` call for all their keys, skipping keys priced Infinity.

**The model** (`buildMip`; main columns first, as in `MainLp`). Let `D = demandScale`, `F = D × horizonSeconds` (rate) or `D` (Make N), `σ = max(s1 × F, 1)` (raw over the horizon, never below one unit), `k = s1 × F / σ` (1 for any real line), `X = STEP_BIG_M × max(x1 over recipe columns)`. For each step recipe column `j` (`kind: 'recipe'`) with options `O_j = model.options(id)`:
- Rate mode, `|O_j| = 1` (option `o`): integer `n_jo ∈ [0, ceil(X·D/ρ_o)]` (`[0, 0]` when `canAdd` is false) with cost `(build_o ?? 0) / σ`; when `owned_o > 0` a column `q_jo ∈ [0, owned_o]` (integer unless `shareOwned`), cost 0; row `(D/ρ_o)·x_j − n_jo − q_jo ≤ 0`.
- Rate mode, `|O_j| > 1`: per option `u_jo ≥ 0` with row `x_j − Σ_o u_jo = 0`, the load row on `u_jo` instead of `x_j`, a binary `w_jo` with `u_jo − X·w_jo ≤ 0`, and `Σ_o w_jo ≤ 1` (one machine option per step).
- Make N: when no option has `owned > 0`, a binary `z_m` per mteId `m` among its options with `canAdd` (one column per mteId, shared by every recipe that can use it), cost `(build_m ?? 0) / σ`, and row `x_j − X·Σ_{o ∈ O_j} z_{m(o)} ≤ 0`; with an owned option, nothing.
- Step charge, when `stepCharge > 0`: every step without `w` columns (Make N, or one or no options) gets a binary `y_j` with `x_j − X·y_j ≤ 0`; its cost, and the cost of each `w_jo`, is `k × stepCharge × (mapId === 'crafting' ? handWeight : 1)`.
- Pools (rate mode): per mteId `m` with `owned_m > 0`, `Σ q_jo over options of m ≤ owned_m`.
- Cleanroom: when `model.cleanroom` has `owned 0` and `build !== null` and a step recipe `needsCleanroom`, a binary `c` with `x_j − X·c ≤ 0` for each such `j`, cost `build / σ`.
- R3's derived-purchase binaries as plan 09 has them, cost `k × weight`.
- Objective: `k × columnCost` on the main columns plus the costs above. No raw-material cap.

`start` = `roundUp(input, x1)` written into the columns (`u` = `x1_j` on the chosen option, `w`, `y`, `z`, `c` = 1 where used, derived binaries = 1 where `x1` buys); it is feasible by construction. `decode(x)`: `support` = step recipe columns with `x_j > 1e-9`; per kept step the option with `w ≥ 0.5` (the only one when `|O_j| = 1`; Make N: an owned option, highest tier then lowest mteId, else the `z = 1` option with the lowest build, null last, then the highest perMachine, then the lowest mteId), `added = round(n_jo)` (Make N: 1 on an added type, 0 on an owned one), `ownedLoad = sig9(q_jo)`; `cleanroom = c ≥ 0.5`. `roundUp(input, x, prefer)`: step recipes with `x_j > 1e-9` in id order; option = `prefer(j)` (the fallback passes the relaxation's largest `u_jo`), else the one with the least `(build ?? 0) × max(0, ceil(load − available − 1e-9))` (Infinity when that needs new machines of an option with `canAdd` false), ties: more available, higher perMachine, lower mteId, where `load = x_j·D/ρ_o` and `available` = the pool's capacity left (shared: a share; direct: whole machines); `ownedLoad` = shared `min(load, left)`, direct `min(ceil(load − 1e-9), left)`; `added = max(0, ceil(load − ownedLoad − 1e-9))`; Make N as in `decode`. `capacityRows` (rate only): per kept step with an option, `(D/ρ)·x_j ≤ added + ownedLoad`.
