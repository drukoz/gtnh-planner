# Build Cost, Machine Sharing and Tier Choice Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The planner counts the raw material to build every machine a line adds beyond what the group owns, with whole machine counts, machines shared by several steps in networked logistics modes (owned and new alike), a machine tier chosen per step, and gathered world blocks made from free inputs where that costs less than digging them — the user's "least raw materials, also for the machines we do not have", "reuse machines we have", "disable the reuse for the whole recipe" and "instead of fewer needless steps we would want to keep that but make the logistics reuse the same machine rather than making 3 machines for example for the cobble to sand conversion".

**Architecture:** A memoized price table prices every candidate machine (its item's crafting chain; a multiblock adds its structure and the hatches it needs at its hatch tier) with the cost analysis the planner already has, from settings that hold only what the memo key hashes. Each step recipe gets its machine options (every eligible tier, overclocked, with build cost — a stand-in for a machine nothing at the tier makes — and owned count) and a sharing key (its programmed circuit and held items). When build cost counts, a build-cost MIP replaces plan 09's step-charge MIP inside `solveLine`: whole new machines per sharing pool — in networked modes (Project Red, AE2) the steps of one machine option and sharing key form one pool, so cobblestone → gravel → sand runs on one forge hammer; elsewhere each step is its own pool — all of one option per step; owned machines of every eligible option free beside them; the step charge kept per step, measured against the raw material with gathered blocks dug; a node limit set from measured lines plus a time guard with an LP-relaxation fallback; the later stages (base, power, canonical) stay inside the machines it bought. With build cost counted, a gathered world block (plan 09's R1) keeps its leaf and the candidate walk also offers its recipes, so digging sand and making it from rock-breaker cobblestone compete on raw material plus machines. Plan assembly, Make N, the build list, Plan 5's layout (one unit for a shared machine, with every recipe's chips or patterns), reuse pins, hook steps and hatches, and the client follow the chosen counts, tiers and sharing.

**Tech Stack:** Node 24 (type stripping) · TypeScript 6.0.3 · highs 1.15.3 · React 19.3.0 · vitest 5.0.3 · @playwright/test 1.63.0 (no new dependency).

**Option rules** (`machineOptions`, in this order):
1. `mapId` `crafting` or `furnace` → `[]` (pseudo steps pay only the step charge).
2. Singleblocks: the map's `basic` machines with `tier ≤ groupTier` and `V[tier] × mapAmps ≥ r.euPerTick` (the rule of `acceptRecipe` and `pickMachine`), each overclocked by `singleblockOverclock(r, { tier, amps: m.amps ?? mapAmps })`.
3. 4. `build = machineBuildCost(pack, prices, m, { recipe: r, tier })` (a multiblock's hatch set at the option's hatch tier, so a higher hatch tier costs more), `solveBuild = build ?? standIn(kind, tier)`, `owned = owned.get(mteId) ?? 0`, and on a multiblock option `hatches` from `hatchSet(pack, m, r, tier)`. 6. **The model** (`buildMip`; main columns first, as in `MainLp`). Let `D = demandScale`, `F = D × horizonSeconds` (rate) or `D` (Make N), `σ = max(s1g × F, 1)` (raw over the horizon with gathered blocks dug, never below one unit), `k = s1 × F / σ` (it turns R3's relative column costs into raw over the horizon; 0 when s1 ≤ 1e-9), `kg = s1g × F / σ` (1 for any real line; it scales the step charge), `X = STEP_BIG_M × max(x1 over recipe columns)`, `ρ_o = o.perMachine` and `b_o = o.solveBuild` (Task 3: the build cost, else the stand-in). On a graph without `alsoMade` goods `s1g = s1`, so `σ`, `k` and `kg` are plan 12's first `σ` and `k`, and every case below that has no gathered block keeps its numbers. Each step recipe column `j` (`kind: 'recipe'`) has options `O_j = model.options(id)` and the sharing key `key_j = model.sharingKey(id)`; a (step, option) pair belongs to the **sharing pool** `poolKey(o, key_j)` when `model.share`, else to a pool of its own, `<id>#<mteId>:<tier>`:
- Rate mode, new machines: per pool `p` with a member whose option has `canAdd`, an integer `n_p ∈ [0, N_p]` (`N_p` = Σ over those members of `ceil(X·D/ρ_o)`), cost `b_o / σ` — the members of a pool share `o` (mteId, tier and, for a multiblock, `hatches`), so one machine has one build; per such member a column `a_jo ∈ [0, X·D/ρ_o]` (machines' worth of the pool's new machines step `j` uses), cost 0; per pool the row `Σ_members a_jo − n_p ≤ 0`. Without `share` a pool has one member and `a_jo ≤ n_p` is the per-step whole machine count `n_jo`.
- Rate mode, owned machines: when `owned_o > 0` a column `q_jo ∈ [0, owned_o]` (integer unless `model.share`), cost 0. Without `share`: per mteId `m` with `owned_m > 0`, `Σ q_jo` over every step's options of `m` `≤ owned_m` (whole machines per step). With `share`: per pool `p` of an mteId `m` with `owned_m > 0` the row `Σ_members q_jo − U_p ≤ 0`, where `U_p` is an integer column in `[0, owned_m]` with the row `Σ_{p of m} U_p ≤ owned_m` when two or more pools of `m` have members, else the constant `owned_m` — an owned machine serves one sharing key (controller ruling 9) and its pool's steps share its busy time.
- One load row per step, in runs: `D·x_j − Σ_o ρ_o·(a_jo + q_jo) ≤ 0` — owned machines of every eligible option count. When two or more options have `canAdd`, a binary `w_jo` per such option with `a_jo − (X·D/ρ_o)·w_jo ≤ 0` and `Σ_o w_jo ≤ 1`: the step's new machines are all of one option (`PlanStep.machine`), owned ones of any option may run beside them.
- Make N: when no option has `owned > 0`, a binary `z_m` per mteId `m` among its options with `canAdd` (one column per mteId, shared by every recipe that can use it: a batch runs its steps one after another, so Make N needs no sharing key), cost the largest `b_o` of `m`'s options over `σ`, and row `x_j − X·Σ_{o ∈ O_j} z_{m(o)} ≤ 0`; with an owned option, nothing.
- Step charge, when `stepCharge > 0`: every step recipe gets a binary `y_j` with `x_j − X·y_j ≤ 0`, cost `kg × stepCharge × (mapId === 'crafting' ? handWeight : 1)` (the `w` binaries cost nothing). `kg`, not `k`: on a line whose least raw material is 0 — glass from rock-breaker cobblestone — `k` is 0 and every step, a hand-crafted one included, would be free; measured against the raw material with gravel and sand dug, a step costs what it costs on plan 09's line.
- Cleanroom: when `model.cleanroom` has `owned 0` and a step recipe `needsCleanroom`, a binary `c` with `x_j − X·c ≤ 0` for each such `j`, cost `cleanroom.solveBuild / σ` (an unpriced cleanroom weighs its stand-in, never 0).
- R3's derived-purchase binaries (`derived`), cost `kg × weight`, with `p_d − M_d·bin_d ≤ 0` on the purchase column `p_d` and `M_d = obj(start) / c_d × (1 + 1e-6) + TINY`, `c_d` being the objective coefficient of `p_d`: what a plan no dearer than the MIP start can buy of it. (Plan 09's M is what its raw lock lets the line buy, `s1 / cost`; this stage has no raw lock, so that M would cut off plans that buy more of a derived leaf to save machines.)
- Objective: `k × columnCost` on the main columns (with `s1 ≤ 1e-9`, where `k = 0`: `F × rawCost / σ`, the raw over the horizon, so buying raw material never becomes free when the least raw material is 0) plus the costs above. No raw-material cap.

`start` = `roundUp(input, x1)` written into the columns (`n_p` = its pool's new machines, `a` = each step's new load, `q` = each option's owned load, `U_p` = the owned machines its pool holds, `w`, `y`, `z`, `c` = 1 where used, derived binaries = 1 where `x1` buys); it is feasible by construction. `decode(x)`: `support` = step recipe columns with `x_j > 1e-9`; per kept step with options, `option` = the one with `a_jo > 1e-9` (at most one), else the option with the largest `ρ_o·q_jo` (ties: higher tier, lower mteId); without `share`, `added = round(n_p)` of its own pool and `newLoad = added`; with `share`, `added = 0`, `newLoad = sig9(a_j,option)` and `pool = poolKey(option, key_j)`; `ownedLoad = sig9(q_j,option)` (0 without a `q` column); `others` = every other option with `q_jo > 1e-9` as `{ option, ownedLoad: sig9(q_jo) }`, largest `ρ_o·q_jo` first, then lower mteId (omitted when there is none); `pools` (with `share`) = per pool some kept step has as its `pool`, `{ option, added: round(n_p), steps }` (`added` 0 for a pool without an `n_p` column). Make N: an owned option, highest tier then lowest mteId, else the `z = 1` option with the lowest `solveBuild`, then the highest perMachine, then the lowest mteId; `added` 1 on an added type, 0 on an owned one, `newLoad = added`. `cleanroom = c ≥ 0.5`. `roundUp(input, x, prefer)`: step recipes with `x_j > 1e-9` in id order, runs `r = x_j·D`; first the owned capacity, options with `owned > 0` by perMachine descending then lower mteId, each taking `t = min(left, r/ρ_o)` (shared: `left` = the room in the owned machines its pool holds plus the whole machines of its mteId no pool holds yet, which then join its pool) or `t = min(left, ceil(r/ρ_o − 1e-9))` whole machines (direct), then `r = max(0, r − t·ρ_o)`; then, when `r > 1e-9`, new capacity of one option: `prefer(j)` when it can add (the fallback passes the relaxation's option with the largest `ρ_o·a_jo`), else the option with `canAdd` and the least `solveBuild × ceil(max(0, r/ρ_o − slack_p) − 1e-9)`, `slack_p` being the room left in its pool's new machines (0 without `share`), ties higher perMachine, lower mteId; it takes `a = r/ρ_o`, and its pool's `n_p = ceil(Σ_members a − 1e-9)`; `option`, `added`, `newLoad`, `pool`, `ownedLoad`, `others` and `pools` as in `decode`; Make N as in `decode`. `capacityRows` (rate only): per kept step with options, `D·x_j ≤ ρ_option·(newLoad + ownedLoad) + Σ_others ρ_o·ownedLoad_o` — with `share` each step keeps the share of its pool the decision gave it, so the later stages never run a pool past its machines.

**Limits.** `solveLp({ ...model, start, maxNodes: opts.buildMaxNodes ?? BUILD_MIP_MAX_NODES, timeLimit: opts.buildTimeLimit ?? BUILD_MIP_TIME_LIMIT_SECONDS })`, timed with `performance.now()`. Accept `optimal`, and `feasible` with `stop !== 'time'`. Otherwise (no whole solution, stopped by time, or `buildTimeLimit ≤ 0`, which skips the MIP): solve the same model with `integer` dropped (the LP relaxation), `roundUp` its main columns with `prefer` = its option with the largest `ρ_o·a_jo`, and add `PlanWarning { code: 'build-cost-approx', text: 'Weighing the build cost of new machines took too long; machine counts are rounded up from an estimate' }`; if the relaxation does not solve, `roundUp(input, x1)` with the same warning. `Solution.buildStats = { seconds, nodes: result.nodes ?? 0, status: result.status (or 'skipped'), stop: result.stop, approx }`.

Shared: the own entries of one `key` (default: the entry's own id) form one **sharing pool** of load `L` = Σ their loads; pools by `L` descending, then their smallest id: a pool takes the room left in the units of its key (index order) while load is left, then whole free units (the next indices) while load is left — any load above 0, so a pool of load 1e-12 takes one free unit —, then `added = max(0, ceil(left − 1e-9))` new machines, and at least one machine in all (with no unit to take, a pool of load 1e-12 gets one new one); every entry of the pool gets the pool's `units` (index order) and `added`, and `pool = 'pool:' + <its smallest id>` when the pool has two or more entries. A unit serves one key (controller ruling 9). With one key per type this never needs more new machines than the MIP (a pool's load is the sum its pool rows bound, and every owned unit replaces one new machine of the type), and it makes the output independent of how HiGHS breaks ties; a pool takes no unit its load does not reach, so `count` and `owned` never exceed what its steps use (plan 09's "N machines where fewer would do").
