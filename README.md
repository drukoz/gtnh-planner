# GTNH Line Planner

Plan efficient automation lines for **GregTech: New Horizons 2.9**, fitted into the base you already have.

- Pick any item or fluid from the pack and a rate (or a one-off batch).
- Get the recipe chain that uses the least raw material at your current tier.
- See where the line goes on a map of your world, how it hooks into your power, logistics and storage, and a 3D view of the build.
- Get the full materials list and build steps, shared with your group so everyone can tick things off.

## Export your pack

You need macOS (the copy uses APFS clones), Node 24, the Java your GTNH 2.9 server runs on (Java 25 works), and the server folder.

1. `npm install`
2. `npm run export -- --server "/path/to/your/GTNH server folder"` — the first time; afterwards just `npm run export`.
   It builds a small exporter mod, makes a copy-on-write clone of the server folder in `.local/export-server` (no world, backups, logs or player files), starts that copy on 127.0.0.1:25566 with a fresh flat world, writes the export, stops the copy and deletes it. Your live server and world are never touched, and the server can keep running; a server folder with symbolic links that lead outside it is refused, because the copy would write through them into your live files. The first run downloads about 2 GB of build tools into `.local/gradle-home`; an export takes a few minutes. Exporter 0.4.0 also writes the unconnected sides of GT pipes, the cracked fluids' textures, the Programmed Circuit's and GGFab's icons and the GT material blocks; an older export still works, with those found by file name. Exporter 0.6.0 also records, for every multiblock it can check, which hatches GregTech's own structure check takes on each of its casings, so the layout puts each hatch where the machine forms; with an older export the planner falls back to its own notes for the common machines and says so elsewhere.
3. `npm run pack:info` shows what was exported; `npm run pack:info -- --find "Iron Dust"` lists the recipes that make something.

Each export lands in `data/export/<pack version>_<date>/` and becomes the active one only after it passes its checks; a failed or interrupted export leaves the previous one active. Run `npm run export` again after a pack update. Exports stay on your machine (`data/` is git-ignored) — never commit them.

All data comes from **your own** copy of the pack and world: recipes are exported from a copy of your server, textures come from your mod jars, and the world is read locally. None of that is stored in this repository.

**Status:** in development. Design: [docs/superpowers/specs/2026-10-17-gtnh-planner-design.md](docs/superpowers/specs/2026-10-17-gtnh-planner-design.md).

## Textures and icons

- The planner draws blocks and items with your own pack's textures. Nothing game-made is in the repository: it is extracted into `data/assets/` (git-ignored) and served only to people logged in to the planner.
- `npm run extract-assets` reads `mods/*.jar` of the server folder in `data/config.json` (or `--server <folder>`), read-only, plus the official Minecraft 1.7.10 client jar. Prism Launcher keeps it at `~/Library/Application Support/PrismLauncher/libraries/com/mojang/minecraft/1.7.10/minecraft-1.7.10-client.jar`, the official launcher at `~/Library/Application Support/minecraft/versions/1.7.10/1.7.10.jar`; otherwise pass `--client-jar <path>` or set `"clientJar"` in `data/config.json`. Its SHA-1 must be `e80d9b3bf5085002218d4be59e668bac718abbc6`. It also copies the chest model sheets (the client jar's textures/entity/chest/ and Iron Chests' textures/model/), which the planner cuts into the chests' faces: run it again after updating the planner, or chests stay plank-coloured.
- To draw textures as your game does, set `"clientInstance"` in `data/config.json` to your GTNH client instance's folder (in Prism Launcher, the instance folder under `instances/`, or its `.minecraft`), or pass `--instance <folder>`. The resource packs enabled in the game then win over the jars, the one at the top of the game's list first; files a pack lacks come from the jars. The instance is only read. `--no-packs` leaves the packs out for one run. Each run lists the packs it used and says what changed since the last run, so run it again after you change packs in the game. Each run compares every pack's version, texture-file count and total size with the last run, so a pack edit that keeps all three is extracted but not reported as a change; to see it reported, run once with `--no-packs` and then normally, or raise the pack's version. Connected textures are not drawn (a wall of casings looks tiled, not seamless), and animated textures show their first frame. The Map's colours follow the new textures. Reload the page once with Cmd+Shift+R afterwards: the browser keeps texture files for up to an hour. Resource packs have their own licences: like every texture, they stay in `data/assets/` on your machine and are never committed.
- `npm run export` also writes `textures.json.gz`, which tells the planner how GregTech draws each machine, casing, cover, material item and fluid. After a pack update, run both again: a running planner picks up new textures from `extract-assets` on its next request; restart it after `npm run export` (as for the recipes). A failed extraction keeps the previous textures.
- When two jars ship the same texture: a mod beats vanilla, then a jar that overrides another mod's texture beats that mod's own jar (GTNewHorizonsCoreMod over gregtech), then the jar whose name sorts last. `data/assets/index.json` lists every conflict.
- Optional icons for everything else: in a **copy** of the client instance (never the one you play with), in a creative single-player world, open NEI options → Tools → Data Dumps → Item Panel. With an empty search box and every collapsible group expanded, dump CSV, then PNG, in the same session; then run `npm run import-nei-icons -- --csv <copy>/.minecraft/dumps/itempanel.csv --png <copy>/.minecraft/dumps/itempanel_icons`. Fluid icons are matched by their display name against the active export, so run `npm run export` first. A dump whose rows and images do not line up is refused. A few items whose names change at random (e.g. Extra Utilities' QED) are left without an NEI icon and listed by the import.
- Without NEI icons, most other textures are found by file name: an item's or block's registry name in its mod's own texture folders (numbered icons such as the Programmed Circuits' included), fluids by name (otherwise GregTech's generic fluid in the fluid's colour), and GT frames, storage blocks, sheetmetal, cells and BartWorks items from their material's texture set.
- Anything without a texture is drawn in a plain colour: by machine kind for blocks, by material for GT items, otherwise a fixed colour per item; on light colours the placeholder's letters are dark. Like every icon, it sits in an item slot as in the game's inventory; in the flow diagram it has a thin dark edge instead.

## Using the planner

1. **One-time setup**, on the computer that runs the planner (Node.js 24):
   - `npm install`
   - `npm run export` reads the recipes from a copy of your server.
   - `npm run set-password` asks for the password your group will share. Only a hash of it is kept.
2. **Start it:** `npm run build && npm start`, then open `http://<this-computer>:8765`. Friends use the port you forward to this computer.
3. **First visit:** enter the shared password, then your name. The name is stored in this browser only and shows next to your ticks.
4. **A project** is one line you want to build, with its own link. Pick what to make, then an amount per minute or per hour, or **Make N (batch)**: a fixed number, made on the machines you already own. Set your tier and the planets and dimensions you can reach. The flow diagram shows each machine step: green boxes are machines you already have, grey ones are new. Click a box to swap its recipe, mark "we already make this" or see the overclock math.
5. **Materials & steps** lists what to build once, what the line uses per hour and where each raw material comes from. Tick rows as you go: everyone sees the ticks live, with the name of who ticked them.
6. **How the planner trades steps for raw material**, in the project's settings (what it counts, and the machines it builds, reuses and shares: [Build cost, reuse and machine tiers](#build-cost-reuse-and-machine-tiers)):
   - **Steps vs raw material** picks how much one more machine weighs against raw material: *Least raw material* (0 %), *Some machines* (2 %) or *Fewest machines* (50 %, the default), each a share of the least raw material the line could use. With build cost counted, every new machine the plan adds (an Auto Workbench too) costs that share of the least raw material over the build horizon, on top of its build, and every machine you already have that a running line uses costs half of it (it needs no building, but it takes pipes, power and space); with build cost ignored, each recipe step must save that share to be built, and the plan never uses more than 25 % above the least. A step crafted by hand in a running line counts as three. The banner says how much more raw material the plan uses than the least, or, where build cost counts, than the leanest line (below), with the cap: *Uses 20% more raw material than the leanest line to save machines (Steps vs raw material: Fewest machines; at most +25 %)*. Projects still on the old 2 % default were switched to *Fewest machines* once, recorded as a "Planner update" change; any other value you picked stays.
   - **Raw material for fewer machines** (*At most +10 %*, *+25 %* — the default — *+50 %*, *No limit*): wherever build cost counts, fewer machines never cost more raw material than this over the leanest line, the plan *Least raw material* makes with the same settings (its machines' build counted, so a line whose least raw material needs machines nobody would build is not the measure); projects stored before it got +25 % once, as a "Planner update". The step charge is measured against the leanest line's raw material where that is more than twice the least raw material, else against the least. At *No limit* the planner works the leanest line out only where it could change the step charge; where it does not, the banner measures against the least raw material. With build cost ignored the setting is not read: the 25 % above holds. Where build cost counts a line may make a good two ways, or buy some of it beside the machine that makes it, on purpose (that machine is full and another would cost more than the raw material it saves, or the line is at its raw cap): the banner and the step's panel say so in a plain note, not as a plan that does not add up.
   - **Count build cost against**, **Build machines at** and **Multiblocks** sit beside it: see [Build cost, reuse and machine tiers](#build-cost-reuse-and-machine-tiers). Crafting-table recipes always run on Auto Workbenches; there is no setting for it.
   - **Supply steps.** Free inputs come from a machine in the line: a rock breaker with water and lava next to it for cobblestone and stone, a pump over an infinite water source or a lava pool, a compressor filling empty cells with air and a canner emptying them. They count in machines, power and the build list. If your group already has a supply, press **We already have a supply of …** on the generator's step (Settings lists them; **Plan its generator again** on the input brings the machine back). A Make N batch, and a tier without a supply machine, take free inputs as given.
   - **Supporting lines.** Alloys, plastics and chemicals are made in supporting lines behind the main line, drawn as groups you can collapse in the flow diagram; **We already make …** on a step of a line imports its material instead. With *Plan supporting lines for alloys, plastics and chemicals* switched off, the line buys a material made within four recipe layers; fluids made from others are always made. Projects made before supporting lines were the default were switched to them once (a settings change by "Planner update"); a project's own choice stays after that.
   - **Ingredient options.** A recipe that takes one of several ingredients (soldering alloy, tin or lead solder) lists every option in the step panel with its raw material per run and the steps its own chain needs; pin one there (Settings lists the pins). The step's swap list shows every way the pack makes the product, those your group cannot use greyed with the reason (tier, dimension, an excluded category or an ingredient out of reach).
   - **Only these come in.** In Settings, list the base materials your group brings to the line: **Use this plan's raw inputs** starts the list from the current plan, the search adds one more. With a list the line buys nothing else: it makes every other good, or says "Nothing makes <good> from your base materials". Water, lava, air and cobblestone always come in. An item on **We already make** that is not on the list is made, with a warning; put it on both lists to buy it. The build list and machine prices do not use the list.
7. If the page says "No recipe export yet", run `npm run export`. To change the password, run `npm run set-password` again and restart the planner; `npm run set-password -- --rotate-sessions` also logs everyone out.

### Build cost, reuse and machine tiers

- **What the planner minimizes:** the raw material the line uses over the build horizon plus the raw material to build the machines it adds beyond those your group owns, each machine priced by its own crafting chain (a multiblock with its structure and exactly the hatches its layout lays; the cleanroom when a step needs one) at the least raw material that makes it on its own, the same whichever other machines are priced, and never dearer than without the override when you make an input cheaper in the cost overrides. **Count build cost against** picks the horizon: *1 hour*, *8 hours*, *24 hours* (the default), *1 week* or *Ignore build cost*. A short horizon favours lines with fewer, cheaper machines; a long one, lines that use less raw material. A **Make N** batch always counts build cost against the batch itself (the setting is hidden there). The banner's cost line says what the line uses an hour and what its new machines cost to build.
- **Goods that only come as a byproduct** of other processing (no ore, mob drop, farm or free supply gives them: Phosphate Dust, for one) cost their price only up to what your group's storage holds, spread over the build horizon (24 hours with *Ignore build cost*; a Make N batch may use the whole stock), and ten times their price beyond it, so a route that does without them wins wherever it costs less. A plan that still buys one beyond the stock says so: *Buys 3,600 a day of Phosphate Dust, beyond the 164 in storage* (at a horizon other than 24 hours it also gives the amount over it: *…, 25,200 over 1 week, …*). Without a world scan the stock is 0.
- **Machines you own cost no build**, also beside new machines of another tier in the same step (one owned Advanced Bending Machine runs beside three new Basic ones), but in a running line each one the line uses pays half a new machine's step charge (**Steps vs raw material**), once however many steps share it. **Reuse machines we have** off counts nothing as owned; the per-type "don't reuse" switch leaves out one machine type.
- **AE2 lines share machines**, owned and new alike: steps on one machine type and tier with the same programmed circuit, the same held items (molds, shapes, lenses, catalysts) and the same fluids run on the same machines while their combined busy time fits, and only the shared machines your group lacks count as build cost. One machine runs at most nine recipes (one ME Interface's processing patterns); more go to another. The layout places a shared machine once, its ME Interface holding every recipe's pattern with blocking mode on, so a run's inputs reach it one recipe at a time. On AE2, cobblestone → gravel → sand runs on one Forge Hammer (beside the Rock Breaker).
- **Project Red lines share no machine:** a GregTech machine keeps re-running the recipe it last ran while the Item Responder Chips keep its inputs topped up, so a second recipe on it would wait for ever. Every step gets its own machines (two Forge Hammers for cobblestone → gravel → sand, each with its own interface pipe), and where one step takes what another makes, the step panel says *One Basic Forge Hammer needs AE2: Project Red cannot feed a machine its own output*, since Project Red never sends an item back into the machine it came from.
- **Machine to machine and EnderIO lines** give every step its own machines (machine to machine's shared pipe cannot hand a machine's output back to it; add-on 15 redesigns that end of the line, and EnderIO waits for its layout to share), and dig their sand.
- **Sand, gravel and the other gathered world blocks** are dug, or on AE2 and Project Red lines made (sand from Rock Breaker cobblestone on Forge Hammers) where that costs less with the machines counted. *Ignore build cost* always digs them.
- **Fewer steps is no goal of its own:** every new machine block still pays its step charge (**Steps vs raw material**, measured against the raw material with gathered blocks dug — or against the leanest line's where that is more than twice it — and never less than the charge on one raw unit), so a free chain of steps is built only where it saves more than its machines cost. Machines you own pay half of it, so a line that owns two of everything runs a free chain on them only where it saves more than that.
- **Crafting-table recipes** run on GT++ Auto Workbenches, priced and powered like any other machine (each recipe on its own: an Auto Workbench crafts the pattern set in its grid). Only a recipe no autocrafter can run is crafted by hand, its step saying why (a tool GGFab makes no single-use version of, or on Project Red and EnderIO lines a stock too large for the bench's safe slots); such a step weighs three. One-off crafting for the build list stays by hand. An Auto Workbench you already own gets its grid and its line's cap on each ingredient in its hook step (AE2: one pattern, blocking off, a Locking Card; Project Red: an Item Stock Keeper Chip; EnderIO: a Limited Item Filter; machine to machine: by hand), and on Project Red the output chest offers back, on an Item Broadcaster Chip, a bench ingredient that also leaves the line, which its maker's Item Extractor Chip sends there first.
- **Machine tiers:** each step's tier is picked by the same sum: overclocking lets a higher tier do the work with fewer machines that cost more, and a multiblock's hatch tier costs its energy hatch. **Machine tier** in the step panel pins one for a step; the tier list marks tiers whose machine cannot be built here. **Build machines at** (*Cheapest tier*, the default, or a tier from LV up to the project's) builds every step's new machines at that tier where a machine of it runs the recipe — else the lowest tier above that does, else the nearest below, and the step says so; a step's own pin wins, and owned machines of every tier still serve. **Multiblocks** *Only when nothing else can do it* builds no new multiblock where a single-block machine that can be built here runs the recipe, and weighs one so heavily elsewhere that any other route, buying the good included, wins; a step that still needs one says so (*Use when cheaper* is the default; owned multiblocks are never weighed so, and cost no build). With *Ignore build cost* nothing weighs a machine, so only the first half holds there: no new multiblock beside a single-block machine that can run the recipe, while a recipe only a multiblock runs is weighed by its raw material alone and its good is not bought instead.
- **Machines that cannot be built here** — no recipe in the pack makes them, or their parts are out of reach at the tier (on GTNH 2.9 the Basic and Advanced Fluid Canner and the Plasma Arc Furnace) — run steps only as far as your group owns them. The line is planned around a step that has none, and when nothing else makes the good the plan says so: *Nothing at ≤ LV makes …: … cannot be built here (no recipe in this pack)*. A pinned tier that cannot be built falls back to the nearest one that can, with a warning; an ingredient option whose only chain needs such a machine says so. A machine that can be made but that the planner cannot price is weighed at the build of the dearest comparable machine, listed as not counted and left out of the build figure.
- **The Materials page** adds the layout's cables, pipes and logistics parts to the machines' build total.
- **Limits of the solver:** the build-cost optimizer is a mixed-integer program decided by its node and iteration limits (50 branch-and-bound nodes, 50,000 simplex iterations), never by time, so the same project always gives the same plan; a 30 s guard only catches a runaway model, and a plan from that fallback says *build-cost-approx*. Where it ends at its limit, its plan is within the gap below of the best it can prove (the gap: how much less the best plan of the model could cost, at most). Measured on the 2.9 export, 1 a minute (steel 10), nothing owned unless said, on a 16-core Mac with no other heavy work (each run started at a 1-minute load under 4 and ran at 2.6–7.4 beside the other real-data planner tests), by `GTNH_LOCAL=1 npx vitest run tests/unit/planner/real-build-cost.test.ts` with the other real-data planner files; the times are medians of three runs, and none fell back to the guard. The first plan of a tier (Electronic Circuit MV, Good Electronic Circuit HV) includes pricing that tier's machines, which the later plans of the tier reuse. ## World map

The planner reads your world so a line can fit into the base you already have. A scan never touches the live server: it reads the newest *complete* backup in `<server>/backups` (a zip that opens cleanly and is at least two minutes old, so one still being written is skipped), or, when there is none, a snapshot copy of the world folder made into the planner's own data folder. It never reads the live world files directly and never writes anything to the server folder, so the server can keep running.

1. **Point it at the server:** set `serverFolder` in `data/config.json` to your server folder (the one holding `server.properties`).
2. **Scan:** open the **World** page and press **Scan newest backup**, or pick one backup from the list. From the shell, `npm run scan` does the same; `npm run scan -- --backup <file>` reads one backup, and `--json` prints the whole scan instead of the summary. Scans run in the background, one at a time, and can be cancelled. When a scan could not read or work out everything (no recipe export yet, side files it could not read, boilers whose steam output the export does not give, steam turbines it cannot trace to any boiler through pipes and tanks, chunks it had to skip), it says so under the scan on the World page and in **Scan notes** at the top of **Found in world**.
3. **Friends without the server folder** upload from their browser on the World page: pick the world folder (or a zip of it). The browser reads it on their computer, finds where players are, the spawn, claimed chunks and chunks people have spent time in, and shows the areas and the total size before anything is sent. A radius slider widens or narrows the area around each spot; the upload button waits until the preview shows the new radius. Only `level.dat` and trimmed region files with just those chunks are sent — player files, claims, quests and everything else never leave their computer. **Advanced: whole dimensions** sends every region file of the dimensions they tick instead.
4. **Use it in a project:** on a project's **Map** tab, choose a finished scan and the base the line is for. The plan then counts the machines and storage already there. A scan that found no base has no map (a scan keeps the map only around bases); a project using it counts the whole world.

Scans live in `data/scans/<id>/` and uploads in `data/uploads/<id>/` (git-ignored). Old scan folders are safe to delete while the planner is stopped.

**The Map tab** shows the base from above, coloured from your block textures, with switchable layers: machines, power cables coloured by voltage tier, logistics (Project Red routed pipes, EnderIO conduits, GT pipes, AE2), storage (filled where a routed or AE2 network reaches it) and the base outline. Drag to pan, scroll or use **+**/**−** to zoom, and move the **Y level** slider to cut through floors. Beside the map, **Found in world** lists the machines and top tier, power networks, logistics networks, stored items with their totals and how many the line's logistics can reach, the world's dimensions and which ones you have visited, prospected veins nearby and the notes. Click the map to pin a numbered note there; everyone on the project sees it.

Power figures are estimates from what is built: clear weather, rain and a 24-hour average. Solar boilers stop about seven minutes into rain, so battery buffers are judged against a rain outage of about eight minutes. Storage whose contents cannot be read reliably is shown as unknown, never guessed.

## Line layout and 3D view

Once a project has a scan and a base, the planner lays the line out block by block: it puts the machines on clear, flat ground next to that base, as close as it can to where it can tap into your power and logistics, and works out every cable, pipe, cover and part needed to hook it up. Those parts join the **Materials & steps** list, grouped into machines, power, and piping & logistics.

- **Logistics**, picked in the project settings:
  - **Machine to machine:** conveyor and pump covers move goods from machine to machine through one shared item pipe (and fluid pipes); every machine's Input Filter is on, and each final product goes into its own output chest through a filtered cover.
  - **Project Red routed:** every machine gets a routed interface pipe with an Item Responder Chip that lists what the machine takes and an Item Extractor Chip that lists what it makes. A new chip lists nothing and so moves nothing, which is why each chip's build step names the items to put in its filter. A multiblock's input bus gets only the Responder Chip and its output bus only the Extractor Chip. The input chest's Extractor Chip lists everything the line takes in, and the output chest takes everything that leaves the line's machines on an Item Terminator Chip: final products, items for steps the line places no machine for, and chance byproducts. Project Red sends an item to a machine that takes it before the output chest. A chip holds 9 items and a pipe 4 chips, and the line warns when that is not enough. You order the raw inputs from the request pipe (or put them in the input chest when your base has no routed network), and you put in the input chest what you make for the line yourself, such as parts you craft by hand or what a machine run by hand makes; the steps name each item.
  - **AE2:** every machine gets an ME interface with one processing pattern, a machine shared by several steps one per recipe (at most nine). The pattern lists the items one run uses up and the items every run gives, never a fluid the line pipes, an item the machine keeps (a mold, a shape, a programmed circuit) or a chance output, so AE2 can encode it. Blocking mode is on, except on a machine that holds an item AE2's blocking mode does not ignore, such as a Packager's schematic. A machine that makes only fluids gets an ME Export Bus on the cable in front of it instead, set to its inputs, with Capacity and Acceleration Cards when it needs them. A machine that takes only fluids or nothing at all (such as a Rock Breaker), or whose item outputs all come by chance, gets no pattern. For each machine without a pattern a warning says that the line relies on what your ME storage holds, or on you. AE2 runs a pattern only when a job needs what the pattern makes, and never for a fluid the line pipes from that machine to another, so a machine whose fluid another machine waits for gets a warning too when no job of the line needs its items, or needs them less often than that fluid: the warning names the machine, the fluid and the machine waiting for it, and says how to keep the first one running. In a loop of machines, such as cells one machine fills and another empties, a job runs each machine for the one it feeds, but never for an item that a craft of that same machine in the job is waiting for: that item comes from your ME storage, and the warning counts runs the same way. Where the machines of a loop feed each other in too many ways to follow every job, the warning says that its share of runs is at most that much. Where other machines also make an item that a machine makes beside its product, a job hands that byproduct to whichever of its requests for it comes first, which may not be the one the plan sends it to, so a machine making that item can run more often than the warning counts. The ME parts' idle power draw counts towards the power check.
  - **EnderIO conduits:** item and ender fluid conduits with every face set; see [EnderIO conduits and the Connections view](#enderio-conduits-and-the-connections-view).
  - The line is only hooked into networks the scan found. The planner never assumes one you have not built.
- **Machines fed two or more kinds of item:** in the routed, AE2 and EnderIO modes such a GregTech machine gets Multi Stack Input off, and such an input bus Limiting mode on, because a machine can start with them the other way and then the first kind to arrive fills every input slot and the line stops. A multiblock that takes its items through two input buses gets Input Separation off where its controller has that setting, as the Electric Blast Furnace and the Pyrolyse Oven do; a controller without it checks its buses together. Each configure step names the tool, the click and the chat line to stop at; for Input Separation, the button in the controller's window and the word its tooltip shows, as most controllers have no tool for it. The line also checks itself for anything that would overfill or block a machine, such as an item no chip takes out or a pattern AE2 cannot encode, and warns with the machine's name and what would go wrong.
- **Multiblock hatches** go only on the casings GregTech's structure check takes them on, each facing the side where its pipe, cable or conduit joins it. With an export of exporter 0.6.0 or later, which casings those are comes from GregTech's own check of each multiblock; for the multiblocks LV–HV lines use, the planner's own notes, read from the pack's GregTech, add what GregTech checks in the controller itself and keep the hatches inside both: an Electric Blast Furnace's input hatch on its bottom layer, a Distillation Tower's output hatches one per layer (built taller for more fluids) and none on its top centre, an Oil Cracking Unit's inputs on one side and its outputs on the other with the catalyst in the middle. A multiblock the planner has no notes for, or whose notes do not fit its exported structure, is placed by GregTech's per-casing rules from the export alone, with a note to check in game that it forms. One that GregTech's check took no plain energy hatch on, because it takes only multi-amp or laser energy hatches or only ones of a higher tier than the export tried (a fusion reactor), gets none: its layout says to place one by hand, and the line's tier and transformers still count its power. With an older export, or for a multiblock the export could not check, the notes cover the common machines; any other multiblock keeps the plain placement, and its layout warns that its hatch positions are not checked against GregTech's rules. A hatch GregTech needs on the machine whatever the recipe moves is placed even when nothing flows through it (a Distillation Tower's input hatch; a Large Bronze Boiler's water and steam hatches, which you fill and empty by hand). The block a Muffler Hatch faces is kept empty and counts in the line's height, so the site you clear and the roof leave it free.
- **Configured parts:** every cover, filter, chip, pattern and programmed circuit gets a build step that says exactly how to set it (face, mode, rate, whitelist, circuit number). Pipes, covers, buses and cables are sized to what they carry.
- **Facing:** a GregTech basic machine has a front and a separate output side. Each one is placed with its output side toward the middle row, where its covers go and where it takes its items, and its front along the row, toward the power head (GregTech never lets the front face up or down). Its place step names that side by the compass, turned with the line, and says how: a sneaking Wrench click on that side sets the front, then a plain Wrench click on the middle-row side sets the output side.
- **Steam machines, Bricked Blast Furnaces and Coke Ovens:** in the routed, AE2 and EnderIO modes a steam machine's output side faces up, because GregTech vents its steam there after every run, so the block above it stays empty (it counts in the line's height, and the roof step says to roof above it) and you pipe its steam into its back (in AE2 mode you also take out what it makes by hand). A Bricked Blast Furnace, which GregTech lets nothing automated fill or empty, and a Coke Oven, which GregTech fills only through its own Coke Oven Hatch (one the layout does not lay), are run by hand: each stands one block back from the middle row with nothing of the line touching it, and its steps say what to fill it with by hand and where to put what it makes. In machine to machine mode both keep their place in the row with no hatch and no power, and a warning says to load and empty them by hand, or to fit the Coke Oven with a Coke Oven Hatch.
- **Input from Output Side:** a machine that takes its items through its output side needs GregTech's "Input from Output Side" allowed. A newly crafted machine has it on; the only control is a Screwdriver right-click on the output side or the front, which switches it each time and also works a cover on that side. The front faces the next machine in the row, so the place step checks it on the middle-row side while the middle row is still empty: for a machine that was broken and placed again, one click, and one more if the chat says "Input from Output Side forbidden". The other steps say to leave it where the chat says "Input from Output Side allowed" rather than to click it.
- **Power:** nothing is connected above its tier; transformer banks step the voltage down one tier at a time. The lowest-tier machines stand next to the power head and higher-tier cables pass over them, so a line with machines of several tiers is placed lowest tier first, each tier in flow order. Machines fed at different tiers stand a block apart, a higher-tier cable crosses the lower runs two blocks up, and no cable of one tier ever touches another tier's cable or a lower-tier machine. A fluid pipe that a higher-tier cable walls in climbs over it, which can make the line taller. GregTech joins a cable to the block you place it against, so the wiring steps say to connect only the drawn sides. Cables and transformers are sized for the volts each machine really gets after cable loss, and wiring that loses more than 10 % is flagged.
- **The tap and the power check:** the line is fed only from a cable on the network's own tier (or, when it has none, the highest tier it has, with a warning), and a hookup is laid only onto a tap whose own cable is rated for the line's amps; it routes around the line and keeps clear of your other-tier cables and lower-tier machines. When the nearest such tap is walled in by the ground or your blocks, the hookup starts from another one, or from another cable of that network on that tier rated for the line, that it can reach; it stays a dashed guide only when none can be reached. The power check judges the line against that one network: whether its spare power covers the line plus every loss and its batteries carry it through rain. It suggests boilers and turbines when they do not. Generators are never placed for you.
- **On the Map tab** the line is solid and everything still to build to hook it up is dashed. Numbered pins mark the site, the power tap, the logistics tap, machines you can reuse and problems, and a build step that names a pin links to it on the map (your notes are N1, N2, …). The **New line** panel sits above what was found. **Move line** (then drag it), **Rotate 90°** and **Auto place** change where the line goes, for everyone on the project. A moved line is checked against the blocks really there, and the layout says how much of the spot the scan did not cover. A spot more than 96 blocks from the base centre is not used, and choosing another base clears it.
- **The 3D tab** shows the line in your pack's textures: drag to turn, right-drag to pan, scroll to zoom and step through the layers with the slider. Hover a block for its name and settings; click it for its facing and recipe. Blocks already in your base show as faint ghosts. Project Red pipes and AE2 cables are drawn solid in the colour of their role with their own pattern on top; GT pipes and cables show their side along their length and their end only where they connect, and a pipe or cable already in your base shows as a faint stub toward the line. A machine or hatch facing up or down keeps its casing's top, bottom and sides where the game draws them; only its front turns. **Show connections** (off until you turn it on; your browser remembers it) draws the Connections tab's links over the line in every logistics mode: each arcs from the face that gives to the face that takes, with an arrowhead pointing the way, high enough to pass over the line's blocks (one that starts right beside a tall multiblock climbs steeply there). In EnderIO mode a link runs from each extract face to every insert face on its channel that takes the item. Otherwise it joins the machines, chests and interfaces on the face of each that shows best: one nothing covers, else one a pipe or cable stands against, where the link starts beside that pipe's core and arms, never inside them (an item beside the item pipe it goes through and never at a fluid pipe, a fluid beside its own pipe), and not on a face that looks away from the other end while another will do. A multiblock's links stay on its own outside, an item's on the bus it goes through and a fluid's on the hatch; a fluid that enters or leaves the line starts at the open end of its pipe. Links are drawn in their EnderIO channel's colour or else the colour of what carries them, as on the Connections tab, with a legend under the view; on an EnderIO line whose flows all ride one channel each good gets a colour of its own instead. Links between the same two faces fan out side by side, a little apart (upward where the faces look along the fan, so none is pushed into a block), and links between big steps are drawn with at most 8 pieces each. Hover a link to name it: it is drawn thicker and the others fade. Click it to mark it and its two faces and read its details. **Focus** (remembered too) shows only the links of the block under the pointer, or of the block you click. The note under the view says how many links are drawn and in how many pieces, how many pieces of big steps and how many links hidden with the hookups it leaves out, and names any it has nowhere in the line to draw (on an AE2 line whose base has no ME network, the raw inputs and final outputs, with that reason). Textures need `npm run extract-assets`; without them blocks are plain colours.
- **Limits:** pipe heat ratings and Project Red crafting chips are not planned, and a GregTech filter cover holds one item, so a machine whose recipes also take another step's item is flagged instead of fixed. In machine to machine mode the output chests sit on the shared pipe behind a filtered cover, which may not stop the pipe from pushing other items in. Check those in game.

## EnderIO conduits and the Connections view

Choose **EnderIO conduits** under **Logistics** in a project's settings. The line then gets one Item Conduit along its middle row and, in the same conduit bundles, one Ender Fluid Conduit network; only a multiblock's fluid hatches get an Ender Fluid Conduit running to them.

- **One connection per machine.** A single-block machine gives and takes items through one face, its output side, and GregTech moves its fluids through that side too (in while its Input from Output Side is allowed, out on any side but its front). So the bundle in front of it serves both: its Item Conduit face and its Ender Fluid Conduit face both point at the output side. Each is set to **Extract**, **Insert** or **In / Out** (**Disabled** where it must not connect); an In / Out face extracts what the machine makes and inserts what it takes, each side with its own filter. Any other single-block machine that is not a GT basic machine keeps an Ender Fluid Conduit to its top; a steam machine vents through its top instead, so no conduit goes there and a warning says to move its fluids by hand. Every face that inserts through a machine's output side reminds you in its build step that the machine must keep Input from Output Side allowed, and the machine's place step asks you to check it.
- **One pipe, filters route.** Every machine's outputs are extracted into the one Item Conduit, and each insert side's whitelist (a Basic, Advanced or Big Item Filter with the exact items it takes, matching meta, and NBT only when the item has it) and priority decide where each item goes: machines that use an item are filled first (priority 1) and the surplus goes to the output chest (priority 0). The Ender Fluid Conduit's own filters route fluids the same way (it has no priority: see the limits below).
- **One channel, more only where filters cannot do it.** The whole line runs on one channel, Red. A face gets another colour only where a filter cannot keep an item away from a face that must not get it, because that face takes the same item from somewhere else: wherever a face could hand an item or fluid to a face the plan does not send it to. A face takes whatever reaches it while it has room (machine counts are rounded up, so most have room to spare), so on one channel the face the item is meant for would run short. That happens when two machines make the same item for two different machines, when the input chest hands out a raw input that a machine gets from another machine or that an output chest collects, and when an open fluid end (no priority, so it takes its turn with the machines) could get a fluid it is not planned to get. If a line ever needs more than 15 channels, a warning names what can reach the wrong face.
- Each configure step names the face's filters and upgrades (for example `In / Out (2 filters, 2 speed upgrades)`) and, for each side, the filter to use, how many of its slots the items fill (Basic 5, Advanced 10, Big 24; an Ender Fluid Conduit's own filter 5) and the items themselves.
- A face whose item goes to several machines is set to round robin, unless the output chest also takes an item a machine takes from that face (EnderIO's round robin takes turns whatever the priority, so the chest would take its turn), and a face that must move more than 8 items/s gets speed upgrades.
- Every extract face is set to **Always active**, because a conduit left at its default waits for a redstone signal.
- Green is left to your base's own network. When the scan found an EnderIO network at the base, the line joins it at the input chest: the storage tap extracts the raw inputs on Light Gray and the input chest's face inserts them on Light Gray, a channel of their own, so the tap stops while the chest is full instead of filling your other storages (on Green, every face's default, it would). Its build step asks you to check that no other face of your network inserts on Light Gray. Without such a network a build step says to fill the input chest by hand.
- Power still runs over GT cables.
- The parts list counts every conduit, filter and upgrade, and the build steps set every face.
- The 3D tab draws every set face as EnderIO does: the dark connector plate with the mode's arrows in the face's channel colours, as the game draws them (Minecraft 1.7.10's dye colours; the Connections tab draws its links in the same colours), and a conduit's see-through parts in EnderIO's dark grey, as in the game. An In / Out face shows both halves, the In arrow in its extract colour and the Out arrow in its insert colour. It also draws every conduit link as EnderIO does: conduits of a bundle that go the same way run side by side where EnderIO puts them (the Item Conduit east of the fluid conduit on a run up, down, north or south, and south of it on a run east or west), one that goes on alone runs down the middle, and where a conduit turns beside another or a bundle's conduits part they meet in EnderIO's connector box, so the conduits of neighbouring cells always join and every connector reaches its face.

The **Connections** tab of a project draws any line, in all four logistics modes, as boxes and links that show every face's settings; drag to move it, scroll to zoom and press **Fit** to see all of it. As in the flow diagram, the goods move along the links toward the box that takes them; **Pause pipes** stops them in both diagrams, and this browser remembers it. When the details panel opens or closes beside it, a fitted picture is fitted again and a moved one keeps its middle. A conduit face's row names its mode and its channel (`In / Out · Red`, or `In / Out · in Blue · out Red` when its sides are on two channels), and an open fluid end that both takes fluid in and sends it out shows under both **Raw inputs** and **Final outputs**. Click a box, a face or a link for the details; a clicked link also marks the face rows it leaves and enters. A flow into or out of a machine the line runs by hand (a Bricked Blast Furnace or a Coke Oven, and in AE2 mode what a steam machine makes) is drawn as carried by hand, in amber with a broken line, and its details give the words of the build step that moves it; in the 3D tab such a link from or to your storage is not drawn, as nothing in the line stands for your storage.

Limits: rates follow EnderIO's default conduit config, so a server that changes the conduit rates in `EnderIO.cfg` may need more speed upgrades or a bigger fluid conduit. A face holds at most 24 filtered items, and more are flagged. Ender fluid conduits have no priority, so when machines take a fluid whose surplus also leaves through an open end, the tank takes its turn with them; the line warns about it. The line plans no redstone signal control (every extract face is simply set to Always active).

## In-game ghost projector

The **GTNH Planner Projector** is a small mod for your own Minecraft client (GTNH 2.9, Minecraft 1.7.10). It draws the planned line in your game as translucent ghost blocks exactly where the layout puts them: faint where nothing is placed yet, green where the right block stands, red where a block or its front is wrong. When every block of a build step is placed correctly, it ticks that step in the project's checklist, in your name. It is a client-side mod: nothing is installed on the Minecraft server, so only the players who want ghosts need it, and if only you want them, only you install it.

### Install

Get `gtnhplannerprojector-<version>.jar` from the person who runs the planner, or build it yourself with `cd projector-mod && VERSION=0.2.0 ./gradlew assemble`; the jar lands in `projector-mod/build/libs/`. Put it into **your client's** `mods` folder (in Prism Launcher: right-click the instance, choose **Folder**, then open `.minecraft/mods`) and start the game. Never put it into the server's `mods` folder.

### Connect

1. On the project page open **In-game projector**, type who the token is for (for example `Steve`) and press **Create token**.
2. Press **Copy** next to the `/planner load …` line (the button says **Copied**) and paste it into Minecraft chat. If the browser will not copy it, which can happen when the planner is opened over plain `http://`, the line is selected instead and the panel says so under it: press Ctrl+C (Cmd+C on a Mac). The token is shown only now; the mod saves it for that project, so afterwards `/planner load <project>` is enough.
3. The mod looks for the planner at the Minecraft server's address on port 8765: for a server at `mc.example.org` that is `http://mc.example.org:8765` (in single player, `http://127.0.0.1:8765`). If yours is elsewhere, also run the `/planner url …` line the panel shows, once.

### Commands

```
/planner load <project> [token] | clear | layer <y|all> | step <n|all|next> | reload | url <url|auto> | xray [on|off]
```

- `/planner load <project> [token]` fetches the project's line and shows all of it. A token is saved for that project; without one, the saved token is used.
- `/planner layer <y|all>` shows only the blocks at height `y` (0 to 255), or every layer.
- `/planner step <n|all|next>` shows only the blocks of build step `n`, numbered as in the project's **Build steps** list (a step that places nothing, such as gathering or crafting, has none to show), or of every step; `next` is the first build step with blocks that is not ticked yet.
- `/planner reload` fetches the latest layout now. The mod also checks about once a minute, so a line you move or rotate in the planner follows by itself.
- `/planner url <url|auto>` sets where the planner is, for example `/planner url http://mc.example.org:9000`; `auto` goes back to the Minecraft server's address on port 8765.
- `/planner xray [on|off]` shows the ghosts through walls and terrain; without `on` or `off` it switches.
- `/planner clear` hides the ghosts until you load a project again.

### Colours

Faint is a block not placed yet, green is the right block (with the right front), red is a wrong block or a wrong front, and bluish is a block the mod cannot check (its step is never ticked automatically). A GT machine's front is the side GT calls its front, the one a plain wrench sets: the face of a hatch or a multiblock controller, but on a single-block machine such as a Basic Macerator its **output side**. A single-block machine also has its own front, where it shows its face, which a sneaking wrench sets; the mod checks both (aim at one that is turned wrong and its name tag says "wrong facing, its front should face … and its output side …"). Its ghost shows the face on the side the front must face and the output overlay on the side the output must face, as the 3D tab and the place step have them. The mod also sees which conduits a conduit bundle holds, and `/planner step` shows a bundle under the step of each conduit it holds: a bundle is green and placed correctly once it holds every conduit the plan puts in it, or, shown for the Item Conduit's step, once it holds that one; otherwise aiming at it says "not all its conduits placed yet". The step that lays the Item Conduit is ticked once the bundles hold their Item Conduits, and the step that lays the fluid conduit only once they hold that too. Update a projector mod older than 0.2.0: it cannot see a bundle's conduits, so it ticks the fluid conduit step by the fluid conduits outside the bundles alone, and never when all of them are in bundles. Blocks in chunks your game has not loaded stay faint, neither right nor wrong. Covers show as their item's icon on the face they go on; covers and settings (the **configure** steps) are ticked by hand. The top left of the screen shows how far the build has got (`Planner: Steel line — 12/40 placed, 1 wrong`); what a ghost is and which way it goes is on its name tag, see **Aiming at ghosts**.

### Aiming at ghosts

Point your crosshair at any ghost, as far away as `maxDistance` (96 blocks by default), even one floating in the air with nothing real next to it. The ghost you aim at gets a **yellow outline** and a **name tag** above it, like a player's name. The tag shows:

- the block's name;
- its state: `not placed yet`, `placed correctly`, `wrong block here`, `wrong facing, its output side should face north`, `can't be checked by the mod` or `not checked yet` (the chunk is not loaded, or the first check has not run);
- which way it goes, while it is not placed correctly: `front should face west`, or `front should face west, output side south` for a single-block machine;
- one line per cover: `cover: <name> on the <side> face`.

A real block in the way stops the aim, just as it blocks your view, but the ghost at that real block's own spot still counts, so aiming at a placed block tells you whether it is right. With x-ray on (`/planner xray on` or the screen's **X-ray** button), real blocks do not stop it. Aiming changes nothing else: right-click still places on the real block your crosshair is on.

When your crosshair passes through two or more ghosts, the top left lists them, nearest first with their distance, and `>` marks the one with the tag:

```
Behind the crosshair (2):
> Steel Pipe Casing 5 m
  LV Input Bus 6 m
```

Under it the top left says what the current step still needs, with counts that drop as you place blocks correctly:

```
Still needed for step 2:
3× Steel Pipe Casing
1× LV Input Bus
```

The list is for the step you picked with `/planner step` or in the planner screen. With **All steps** it is for the first step with blocks that is not ticked yet. A block the mod cannot check is listed last, as `2× Item Conduit (can't check)`.

### The planner screen

The planner screen is a 3D model of the line, with buttons for what the commands do. Open it with the small **P** button above the top-right corner of your inventory (the `E` screen), or bind a key: in **Controls**, under the **GTNH Planner** heading, **Open the planner screen** has no key until you pick one.

- **The model** is on the left, coloured like the ghosts. Drag to turn it, right-drag to move it, scroll to zoom. Hover a block to see the same lines as its name tag. Blocks outside the step or layer you picked are drawn very faint, but you can still hover and click them.
- **Click a block** to close the screen and find it in the world: it gets a cyan outline and its name tag, through walls and at any distance, and the top left says `Finding: LV Input Bus — 23 blocks NE, 2 up`. Finding stops when you aim at that block, open the screen again, run `/planner clear`, or after a minute.
- **The step list** is on the right: **All steps**, then every build step, with done steps ticked. Click a step to show only its blocks, like `/planner step <n>`. Steps that place nothing (gathering, configuring) are listed but cannot be picked. The blocks the picked step still needs are listed under it.
- **The bottom row** has a layer slider (like `/planner layer`), **All layers**, **X-ray** (like `/planner xray`), **Reload** (like `/planner reload`) and **Hide ghosts** / **Show ghosts**. Hide ghosts hides the ghosts, the yellow outline and tag, and the **Behind the crosshair** list. It keeps the line loaded, the progress line and the needs list, and the top-left progress line ends with `· ghosts hidden`. A block you are finding stays outlined with its tag, and aiming at it still ends the finding. Hide is not saved, so the ghosts are back after a restart. `/planner clear` is different: it forgets the line.
- **Nothing loaded:** the screen says to paste the `/planner load …` line from the project's **In-game projector** panel, and shows one button for each project you have already connected. Press one to load it. The first connection still needs the pasted line, since it carries the token.

The screen works from the same settings as the commands: pick a step in the screen, then type `/planner step all`, and it follows. The line is still re-fetched about once a minute, and an open screen follows what changed. The game does not pause while the screen is open. Press `E`, the planner key (if you bound one) or Esc to close it.

### Troubleshooting

- **"Cannot reach the planner …":** is the planner running, and is its port forwarded to you? Set its address with `/planner url <url>`.
- **"The planner refused this token …":** the token was revoked. Create a new one in the project's **In-game projector** panel and run its `/planner load` line.
- **Nothing is drawn:** you may be in another dimension than the line (the top-left line names the line's dimension), a filter may be on (`/planner layer all`, `/planner step all`), you may have pressed **Hide ghosts** in the planner screen (press **Show ghosts**), or you may be farther from the ghosts than `maxDistance` (96 blocks by default; raise it in `config/gtnhplannerprojector.properties` in your instance's Minecraft folder and restart the game). If the top-left line says the project is not placed in the world yet, pick a world scan and base on its Map tab.
- **The top-left lines show but the ghosts are invisible:** set `useDisplayLists=false` in `config/gtnhplannerprojector.properties` and restart the game.

### Privacy

A token lets whoever holds it read that one project and tick its build steps, nothing else: it cannot open another project, tick materials or change settings. The mod keeps it in your `config/gtnhplannerprojector.properties`, so keep that file private, and revoke tokens you no longer use (**Revoke** in the panel). Tokens travel over plain HTTP unless the planner is behind HTTPS.
